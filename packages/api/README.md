# @osfpm/api

The HTTP API of OSFPM. Every client, including the future web app, uses this one public API. It is built on Fastify 5, with Zod as the single source for validation, types and the OpenAPI document.

What is here: configuration, start-up (migrations, the permission catalogue and, on a fresh install, the one-time setup code), the server's keys (the identity key published at `/.well-known/osfpm/server-key`, and the data keys that encrypt authenticator secrets), the admin command line (`info`, `doctor` and the commands that change the keys), logging, error mapping, health and meta routes, the OpenAPI document, first-run setup (two routes, and a gate that keeps the rest of the API closed until the first administrator exists), authentication of a signed-in user by session cookie, with four routes for that user's own sessions, sign-in by password (with an optional authenticator code), by recovery code or by passkey, five routes to secure the account, five to add, list, rename and revoke passkeys, six for members and invite links (list the members, make, list and revoke invites, look at an invite and accept it), and two for a person's own delivery preferences (`GET` and `PUT /me/preferences`). Admin reset links come in P-03b4c and API tokens in P-03b5. The first administrator is made by first-run setup and more people join by invite; there is no data route. Do not expose it beyond your own machine.

## Run it

Set exactly one database setting, `OSFPM_PUBLIC_URL`, and with PostgreSQL `OSFPM_KEYS_DIR`, then start the server from the repository root:

```sh
# Small install: PGlite, stored in a directory
OSFPM_PUBLIC_URL=http://localhost:3000 OSFPM_DATA_DIR=./data pnpm --filter @osfpm/api start

# Standard install: PostgreSQL 16 or later; the keys need a directory of their own
OSFPM_PUBLIC_URL=https://osfpm.example.org DATABASE_URL=postgres://osfpm:<password>@127.0.0.1:5432/osfpm OSFPM_KEYS_DIR=/var/lib/osfpm/keys pnpm --filter @osfpm/api start
```

The server keeps its keys in a key directory (`OSFPM_KEYS_DIR`; with PGlite, `<OSFPM_DATA_DIR>/keys`). **Back it up with the database.** See [Server keys](#server-keys).

Then ask it something:

```sh
curl http://127.0.0.1:3000/api/v1/health
curl http://127.0.0.1:3000/api/v1/meta
```

On a fresh install the server also prints a **setup code** to standard error, and every route but those above answers 503 `setup-required` until the code has been used. See [First run](#first-run).

`Ctrl+C` or `SIGTERM` stops it in order: it stops accepting requests, lets requests in flight finish, closes the app, closes the database, then exits with code 0. A second signal during shutdown is ignored, and if shutdown takes longer than ten seconds the process exits with code 1.

`start` runs the TypeScript source through `tsx`, a development-only dependency. Production runs compiled JavaScript; the build step and an exports map for the core come with the production image.

## Start-up

The server does this, in this order:

1. Opens the database. A PGlite data directory that cannot be opened stops the start.
2. **Listens.** From here a supervisor's probe finds a live process.
3. Runs pending migrations, unless `OSFPM_AUTO_MIGRATE` is `false`. With it off, the database must already be migrated, or step 4 fails.
4. Syncs the permission catalogue: every `*_PERMISSIONS` list the core declares goes into the `permission` table, in one transaction, so all of them or none. That transaction starts by narrowing the managed roles' `all-projects` grants of any permission that is now flagged sensitive (`narrowManagedSensitiveGrants`; see the Administrator role under [First run](#first-run)). The core owns the list of lists (`PERMISSION_LISTS` in `packages/core/src/access/permission-lists.ts`) and the API imports it; a core test fails when a module declares one that is not in it.
5. Makes the single `installation` row if it does not exist and, until first-run setup is complete, issues a setup code (revoking the earlier one) and prints it to standard error. See [First run](#first-run).
6. Gives the Administrator role of every organisation the permissions that were added since it was made, in one transaction (`topUpAdministrator`). See [First run](#first-run). The role is managed, so this is the only way a new permission reaches the administrators. A count goes in the log, and one audit event for each organisation that got any.
7. Opens every route.

**It marks the database as in use first.** Before step 3, and again at the start of every attempt, the server marks its database as in use, so that an admin command that needs every server stopped (see [Admin command line](#admin-command-line)) never runs beside it. On PostgreSQL it takes a shared advisory lock on one connection of its pool, which it keeps until it stops; a command that is running only makes the server wait, as an unreachable database does: one warning line per attempt that says an admin command is using the database, and nothing more. With PGlite it takes a lock file, `osfpm.lock`, in the data directory before it opens the directory, and refuses to start, with exit code 1, if another process holds it.

**While it starts (steps 3 to 7),** `GET /health` answers 200, `GET /health/ready` answers 503, and every other route answers a 503 problem `starting`: the same for a caller with a cookie and one without, before the session, the Origin or the rate limit are looked at, because the database may not be migrated or reachable yet. An unknown path is still a 404. A route that does not say `config: { availableWhileStarting: true }` waits, so a new route cannot be open by accident; only the two health routes say it. `/health/ready` keeps answering 503 after that until a trivial query to the database is answered.

**If the database cannot be reached** (the connection is refused, reset or times out, the host is not found, or PostgreSQL is starting up or shutting down), the server does not exit. It tries steps 3 to 7 again after a wait of one second, doubling after each failure up to thirty seconds, for as long as it takes (`STARTUP_RETRY` in `src/startup.ts`), and stays at 503. It writes one warning line per attempt: the attempt number, the wait, the error's class and its short system code, such as `ECONNREFUSED`. A line never holds the host, the URL or the password. Migrations are safe to run again. A stop signal ends the waiting at once.

**Any other failure stops start-up.** A wrong password, a database that does not exist, a failed migration, a `PermissionSyncError` and a `ServerKeysError` (the key directory is not this database's, see [Server keys](#server-keys)) are not cured by waiting. The server writes one log line with no request in it that holds the error's class name only, prints a message and exits with code 1. A `PermissionSyncError` (a permission was flagged sensitive while a role an organisation made still holds an `all-projects` grant of it) prints its own message, which names the permission and the roles and says the release must ship a migration that narrows them, and no stack. Any other failure prints a generic line with the error's class name and system code: driver messages can hold SQL and connection details.

## First run

A fresh install has no organisation and no user, so nobody can sign in. **First-run setup** (spec card SC-10, decision D-56) is how the first administrator is made: whoever installed the server and holds the setup code it printed creates the first organisation, its Administrator role and the first administrator account.

**The setup code.** After the migrations and the permission sync, the server makes the single `installation` row if it is missing (with a new UUIDv7 as this server's id, never replaced) and, while setup is not complete, issues a one-time setup code and prints it once to **standard error**, in a marked block, outside the JSON logger:

```
=== OSFPM first-run setup ===
Setup code: 7K2M-9QXD-4RTV-HB8N
Open https://osfpm.example.org and enter this code within 24 hours.
A new code is printed on every restart until setup is complete.
=============================
```

This is the only secret OSFPM ever prints. It is written by hand in `runStartup`, after the transaction that saved it has committed, so it never passes through the logger (which keeps masking codes and tokens), and nothing else holds it: the database stores only its hash. It works once and for 24 hours. A restart prints a new code and revokes the old one, and prints nothing once setup is complete; the one line the log holds says only that a code was written to standard error. If several servers start together on one database, the last to issue a code is the one whose code works. The address printed is `OSFPM_PUBLIC_URL`, and the installation's `base_url` is that origin at the first start: changing `OSFPM_PUBLIC_URL` later does not change it.

**The gate.** Until setup is complete, every route but `GET /health`, `GET /health/ready`, `GET /meta`, `GET /openapi.json`, `GET /.well-known/osfpm/server-key` and the two setup routes answers a **503** problem `setup-required`. It is the same with a cookie, a foreign `Origin` or neither, and it is decided before the session, the Origin or the rate limits are looked at: nobody can hold a session yet, so a route that needs one does not answer 401. An unknown path is still a 404. A route says `config: { availableBeforeSetup: true }` to answer before setup; one that says nothing is closed, so a new route cannot be open by accident. `GET /meta` carries `setupRequired`, true until setup is complete, so a client knows to show its setup screen. The app asks the database until it sees setup complete and then remembers it, so a finished install pays nothing for the gate.

**The two routes** are `auth: none`, count against the strict limit per address (together with the login routes), and are a 404 once setup is complete.

- `POST /api/v1/setup/check` takes `{ code }` and answers 204 if the code is live, without using it up, so a setup screen can check it before it asks for details. Every other case, whether the code is unknown, expired, replaced by a newer one, used or not shaped like a code, is the same 401 `setup-code-invalid`.
- `POST /api/v1/setup` takes `{ code, organisation: { name, country, baseCurrency, locale?, timeZone? }, admin: { email, displayName, password? } }` and, in **one transaction**, creates the user (active, the address kept in lower case), sets the password if one was given (under the policy), creates the organisation, its **Administrator** role, the user's owner membership linked to that role, marks setup complete, and makes a session (method `setup`) and sets the cookie. It answers 201 `{ user, organisation, mustSecureAccount }`, uncached. A failure at any step leaves nothing, and the code stays usable. `country` is two capitals (`GB`) and `baseCurrency` three (`GBP`), the same as the database's own checks; `locale` and `timeZone` default to `en` and `UTC`.

**The Administrator role** holds every permission. A permission that is not flagged sensitive is granted to all projects (which also counts in the organisation), so the administrator sees and edits every production's ordinary data without being a member of each. A sensitive permission is granted in the organisation only and never to all projects: sensitive crew data, contract amounts and cost amounts still need membership of the production (decision D-55; CLAUDE.md, Privacy rule).

The role is **managed** (`role.managed`): the server makes it and keeps it, and an organisation cannot edit or delete it or its permissions. A service that edits a role refuses it with `ManagedRoleError`, a 409 `role-managed`, and a database trigger refuses the write when a service skipped that check. Each time the server starts it **tops the role up**: a permission that a release declared after the role was made is granted the way setup grants it (all projects for an ordinary permission, the organisation only for a sensitive one), through the write helper as the system, and audited as `auth.administrator-role-topped-up` once for each organisation, with a count and no permission key. It only adds: it takes nothing away and changes no grant that exists. The one exception is a permission that a release newly flags sensitive: a sensitive permission never reaches all projects, so before the permission sync, in its transaction, the server narrows every `all-projects` grant of such a permission on a managed role to the organisation only, audited as `role.grant-reach-reduced` once for each grant (the role, the permission, both reaches). Roles an organisation made are not touched: their grant still stops start-up, and the release must ship a migration for them.

**Without a password** the session has the recovery scope and the answer says `mustSecureAccount: true`: the administrator may read who they are, sign out, set a password (`PUT /api/v1/auth/password`) or add a passkey, and every other route answers 403 `account-recovery-required` until they do, by the rule that a session opened by a recovery code already follows (see Authentication).

**Refusals.** A code that does not work is one 401 whatever is wrong with it, and is audited without the code. Of two requests at once with the same code, the one that loses gets that same 401; a request after setup is complete is a 404. A password the policy refuses is a **422** `password-refused`, the same answer as `PUT /api/v1/auth/password` gives for it everywhere, with the reason in `errors[0].code` (at `admin.password`) and what to do in `detail`; it leaves the code unspent. A body that is not shaped right is a 400 `validation-failed` that lists the fields and never their values. A `POST` with no `Origin`, or with one that is not the public origin, is a 403 `origin-mismatch`, cookie or not: both routes say `config: { requireOrigin: true }`, like every route that makes a session (see the cross-site check). A browser always sends the header; a script or `curl` must send `Origin` itself, as the example below does.

**After setup** both routes answer 404, the same as a path that is no route, and the rest of the API opens at once, with no restart.

```sh
curl -X POST http://127.0.0.1:3000/api/v1/setup -H 'Content-Type: application/json' -H 'Origin: http://127.0.0.1:3000' -d '{
  "code": "7K2M-9QXD-4RTV-HB8N",
  "organisation": { "name": "Demo Pictures", "country": "GB", "baseCurrency": "GBP" },
  "admin": { "email": "ada.demo@demopictures.example", "displayName": "Ada Demo", "password": "<a long passphrase>" }
}'
```

The code, the password and the session token are never logged, never in an error body, never in an audit event and never in a change event; the token goes only into the cookie. The checks are in `src/setup/` (see its README).

## Invite links

An administrator brings more people into the organisation with an **invite link** (spec card SC-10, decision D-57). OSFPM sends no email: it makes a one-time link, shows it once, and the administrator passes it on by any channel. The rules are in the core (`packages/core/src/auth/invites.ts`); the routes are in `src/invites/`.

- **Who may.** `members:read` lists the organisation's members and `members:invite` makes, lists and revokes invites. Both are organisation-level and not sensitive, and the start-up top-up gives both to the Administrator role. A caller who lacks the permission, is not a member, or names an organisation that does not exist gets the same 403, so the answer never says which.
- **Making one.** `POST /api/v1/organisations/:organisationId/invites` takes `{ email?, tier, roleIds, expiresInDays? }` and answers 201 `{ invite, link }`. The tier is `admin`, `member`, `supervisor` or `guest`, never `owner`. The invite lasts 7 days unless `expiresInDays` (1 to 30) says otherwise. With an `email` only that address can accept it; it is kept in lower case and is never logged or audited.
- **The link is `<OSFPM_PUBLIC_URL>/invite#<token>`, and it is in that response only.** The token is after the `#`, the **fragment** of the address. A browser never sends the fragment to a server, a proxy or in a `Referer` header, so the token does not reach OSFPM, a reverse proxy's access log or a site the page links to by being opened. The web app, which comes later, reads the fragment and sends the token in the body of `POST /invites/inspect` and `/accept`. Only the SHA-256 hash of the token is stored, made the same way as a session token's, so no list returns a link, a token or a hash, and the create response is not cached.
- **No escalation.** An invite gives only what the person making it holds: for every grant on every role it attaches, they must hold the same permission in this organisation at the same reach or wider (an `all-projects` grant needs an `all-projects` grant). There is no exception for an owner, because a tier grants nothing by itself (decision D-51). Otherwise the answer is a 422 `invite-exceeds-own-access` that lists the permission keys in `errors`. A role of another organisation, a project role, a deleted role or one that is not there is a 400.
- **Looking at one.** `POST /api/v1/invites/inspect` takes `{ token }` and answers the organisation's name, when the invite ends and whether it names an address (not which). It uses nothing up. It takes no session (`auth: 'none'`), counts against the strict limit per address and needs the right `Origin`.
- **Accepting one.** `POST /api/v1/invites/accept` takes `{ token, account? }` (`auth: 'optional'`, strict limit, `Origin` required) and answers 201 `{ user, organisation, mustSecureAccount }`. With a **full session cookie** the signed-in user joins as themselves and `account` must be left out (400); a recovery session cannot accept (403 `account-recovery-required`), and a cookie that is invalid or expired is a 401, as on a route that needs a session, even though `optional` would let it through. With **no cookie** `account` is required: `{ email, displayName, password? }`. The route makes the account, the membership with the invite's tier and roles and a session (method `invite`, cookie set), in one transaction. With no password the session has the recovery scope and the answer says `mustSecureAccount: true`, as in setup. A password the policy refuses is a 422 `password-refused` at `account.password`.
- **One answer for a bad token.** An unknown, expired, revoked or already used token is the same 401 `invite-invalid`, from both routes, with one body. The cause is in the audit trail alone. The loser of two accepts of one token at once gets it too.
- **Refusals that leave the invite usable:** a 422 `invite-email-mismatch` (the invite names another address), a 409 `already-member` (the signed-in user already belongs; a removed membership counts too, because a removed member cannot rejoin by invite yet) and a 409 `account-exists`. A failure at any step leaves nothing: no account, no membership, and the invite unused.
- **Accepted risk: `account-exists`.** When someone holding a live invite opens it with a new account for an address that already has one, the 409 `account-exists` tells them an account exists for that address. The invite is the capability, so this is as much as the holder of the link could learn by trying to sign in, and the answer is what the person needs ("sign in, then open the link again"). It is not offered to anyone without a live invite, and the strict limit per address applies.
- **Audit.** `auth.invite-created` (the invite, the organisation, the tier, the role ids, the expiry and whether an address is set), `auth.invite-inspect-failed` and `auth.invite-accept-refused` (a reason code), `auth.invite-accepted` (the invite, the user and whether the account is new) and `auth.invite-revoked`. A refusal is committed before it is answered, so its event is kept. Listing the members is not audited. No event, log line, change event or error body holds a token, a hash, an invite's address or a password.
- **Races.** Two accepts of one token make one membership, and an accept and a revoke end with the invite used or revoked and never both, by the invite row lock; the accept takes the organisation's change counter first (the lock-order rule in CLAUDE.md). PostgreSQL-only tests show it.

What is not here: role editing, removing a member, changing a tier and any email sending. Admin reset links are in the next section.

## Admin reset links

An administrator helps a member who is locked out (a forgotten password, a lost authenticator device, a lost passkey) with a **reset link** (spec card SC-10, decision D-57). OSFPM sends no email: it makes a one-time link, shows it once, and the administrator passes it on by any channel. Opening it signs the person in with a recovery-scope session, where they must set a new password or add a passkey. The rules are in the core (`packages/core/src/auth/access-reset.ts`); the routes are in `src/access-reset/`.

- **Who may.** `members:reset-access` makes and revokes a link. It is organisation-level and not sensitive, and the start-up top-up gives it to the Administrator role. A caller who lacks it, is not a member, names an organisation that does not exist, or names a person who is not a member of the organisation (or not a user at all) gets the same 403, so the answer never says which.
- **Making one.** `POST /api/v1/organisations/:organisationId/members/:userId/reset-link` takes `{ expiresInHours?, removePasskeys? }` (a JSON object, `{}` for the defaults; a request with no body and no `Content-Type` means the same, while a body that says it is JSON must be an object) and answers 201 `{ link, expiresAt, removePasskeys }`. It lasts 24 hours unless `expiresInHours` (1 to 72) says otherwise, and `removePasskeys` says whether using it also revokes the person's passkeys (false unless asked: the passkeys stay). A person has one live link: a new link revokes every earlier link of theirs that was neither used nor revoked, expired ones too, and the database refuses a second one (`access_reset_live_unique`, a partial unique index). `DELETE` on the same path revokes the live link, 204, or answers 404 when there is none.
- **The link is `<OSFPM_PUBLIC_URL>/reset#<token>`, and it is in that response only.** The token is after the `#`, the **fragment** of the address, which a browser never sends to a server, a proxy or in a `Referer` header, as for invites. The web app, which comes later, reads the fragment and sends the token in the body of `POST /access-reset/inspect` and `POST /access-reset`. Only the SHA-256 hash of the token is stored, made the same way as a session token's, and the create response is not cached.
- **Who may reset whom.** Seven rules, checked when the link is made and **again when it is used**, with the person who made it as the actor. When one fails at use, the link is refused with the same 401 as any bad link, nothing is changed, and the audit event records the reason.
  1. The actor holds `members:reset-access` in the organisation, and can still sign in.
  2. The person is not the actor: people reset themselves with their recovery codes (422 `cannot-reset-self`).
  3. **Every membership the person has, in any status, is in this organisation** (422 `user-in-other-organisations`). A reset signs whoever holds the link in as the person, and clears their password, authenticator and recovery codes. If the person belongs to another organisation too, the administrator of this one would be taking over an account that is also another company's. Such a person recovers with their own recovery codes, or through the server's own administration tool (P-09a2).
  4. An owner can only be reset by an owner (422 `owner-reset-needs-owner`).
  5. No escalation: the actor holds every permission the person holds in the organisation, at the same reach or wider (an `all-projects` grant needs an `all-projects` grant), the rule invites use. There is no exception for an owner (422 `reset-exceeds-own-access`, the permission keys in `errors`).
  6. The person's account is active: not disabled, not only invited, not deleted (422 `user-not-active`).
  7. The person's membership of this organisation is active: not removed, and not still only an invitation (422 `membership-not-active`). A link is for someone who belongs to the organisation now, so a membership that was removed after the link was made ends the link too: using it is refused like any bad link, and the audit event says why.
- **Looking at one.** `POST /api/v1/access-reset/inspect` takes `{ token }` and answers `{ expiresAt }` and nothing else: not the name or the address of the person, since anyone who holds the link could read them. It uses nothing up. It also checks the rules, so a page does not show as good a link that using it would refuse. It takes no session (`auth: 'none'`), counts against the strict limit per address and needs the right `Origin`.
- **Using one.** `POST /api/v1/access-reset` takes `{ token }` (`auth: 'none'`, strict limit, `Origin` required) and answers 200 `{ user, mustSecureAccount: true }` with the session cookie (method `reset`, scope `recovery`), all in one transaction. A session cookie the browser already has is ignored, not read and not cleared, and the new cookie replaces it. A use checks the rules again, ends every session of the person, clears their password, removes their authenticator app and their recovery codes, revokes their passkeys if the link said so, and marks the link used. A failure at any step leaves nothing, and the link stays usable.
- **The session may only secure the account.** It may read who the person is, sign out, set a password (which makes it full), enrol or confirm an authenticator, make recovery codes, and add, list and revoke passkeys, so a person whose device was lost can remove its passkey. Revoking their last way to sign in is still refused (409 `last-sign-in-method`). Every other route is a 403 `account-recovery-required`.
- **One answer for a bad link.** An unknown, expired, revoked or already used token, and a link that a rule now refuses, is the same 401 `reset-link-invalid`, from both routes, with one body. The cause is in the audit trail alone. The loser of two uses of one token at once gets it too.
- **Audit.** `auth.access-reset-created` (the link, the organisation, the person, the expiry and `removePasskeys`), `auth.access-reset-revoked` (reason `manual` or `superseded`), `auth.access-reset-inspect-failed` and `auth.access-reset-use-refused` (a reason code), and `auth.access-reset-used` (the person, the number of sessions revoked, whether a password was cleared and an authenticator removed, the number of recovery codes and passkeys removed). A refusal is committed before it is answered, so its event is kept. No event, log line, change event or error body holds a token, a hash, a password or an address.
- **Races.** Two uses of one token use it once, and a use and a revoke end with the link used or revoked and never both, by the link row lock. A use and an accept of an invite that gives the same person a second membership exclude each other by the user row lock, taken `FOR UPDATE` and last by both (the lock-order rule in CLAUDE.md): the use finishes before the new membership exists, or it sees it and is refused. Making a link takes the same row `FOR UPDATE`, so two links made for one person at the same moment queue on it: both are made, and the later one is the live one. The rules are judged again under that lock, so no link is made for a person who has just joined another organisation or been disabled. A create never waits for a link row while it holds the person's row, because a use holds its link row and waits for the person's row, and that would be a deadlock. PostgreSQL-only tests show it.
- **Revoking is open to any administrator with `members:reset-access`.** `DELETE` does not ask the rules for who may reset whom, so an administrator who is not an owner can revoke the link made for an owner. That is deliberate: revoking only removes access and gives nobody any.
- **Limits to know.** Making a link at the very moment someone opens the person's earlier link, or revokes it, can fail once: the earlier link is held by the other request and cannot be replaced, the database refuses the second live link, nothing is written, and the answer is a 409 `reset-link-busy`. Making the link again works; the server does not retry.

What is not here: the command-line tool for a locked-out sole administrator (P-09a2), removing or suspending a member, changing a tier or a role, and any email sending.

## Personal API tokens

A person can make a **personal API token** for a script or a personal tool (spec card SC-10, decisions D-17 and D-68). A token acts as its owner, narrowed to one organisation (or one project in it), to reading or writing, and to a short list of sensitive permissions, and it never reaches further than its owner does. Each organisation has a switch for them that is **off until an administrator turns it on**. The rules are in the core (`packages/core/src/auth/api-tokens.ts` and `packages/core/src/access/credential.ts`); the routes are in `src/api-tokens/`, and the plugin that reads the header is in `src/auth/`.

- **Two switches, both off by default.** `api.personal-tokens` allows tokens at all, and `api.personal-tokens.sensitive` allows a token to carry a sensitive scope; the second can only be on while the first is (a 400 otherwise). `GET` and `PUT /api/v1/organisations/:organisationId/api-settings` read and change them and need `api:manage`. Turning one **off** takes effect at once, in the same transaction: tokens off revokes every live token of the organisation (reason `switch-off`) and turns the sensitive switch off too, and the sensitive switch off revokes every live token that has a sensitive scope. Turning one back on restores nothing. Every request a token makes checks both switches again, so a token is refused even if a revocation was missed.
- **Who may.** `api:tokens` makes a token. **Listing and revoking your own needs no permission**: it only shows a person what is theirs and takes access away, so a person who lost `api:tokens` can still see and end the tokens they made. Those two are self-service (no session is a 401, a recovery session a 403, and someone else's token is a 404 for everyone, so a list with nothing of yours is just empty). `api:manage` changes the switches and lists and revokes anyone's tokens (metadata only, never a hash). Both permissions are organisation-level and not sensitive, and the start-up top-up gives both to the Administrator role. A caller who lacks the permission, is not a member, or names an organisation that does not exist gets the same 403 on a route that needs one. **A token needs its owner to hold `api:tokens` in the organisation every time it is used.** Taking the permission from a person makes their tokens fail (the same 401 `invalid-token`, with `permission-missing` in the audit trail) without revoking them, and giving it back makes them work again. The person can still list and end them, and so can someone with `api:manage` (`GET …/api-tokens?scope=all`, then `DELETE`), and turning the switch off ends them all.
- **Making one.** `POST /api/v1/organisations/:organisationId/api-tokens` takes `{ name, projectId?, access, expiresInDays?, noExpiry?, sensitivePermissions? }` and answers 201 `{ token, apiToken }`. It needs `api:tokens` and the organisation's switch on (422 `api-tokens-disabled`). `access` is `read` or `write`. A `projectId` must be a project of the organisation that the person can reach, or the answer is a 422 `project-not-available`: one body whether the project does not exist, was deleted, is another organisation's or cannot be reached, so it says nothing about projects that are not the person's (a value that is not an id is a plain 400).
- **The token is `osfpm_pat_` and 43 characters (32 random bytes in base64url), and it is in that response only.** Only the SHA-256 hash of its random part is stored, made the same way as a session token's (the fixed `osfpm_pat_` start is public and is not hashed), with a `prefix` (`osfpm_pat_` and the first 8 characters) so that owners and administrators can tell tokens apart. No list returns a token or a hash, and the create response is not cached. **Secret scanning:** the fixed `osfpm_pat_` start is there so that secret scanners, such as GitHub's, can recognise a token that leaks into a repository (the pattern is `osfpm_pat_[A-Za-z0-9_-]{43}`). A token that leaks should be revoked at once.
- **Set an expiry.** `expiresInDays` is 1 to 3650 and is 365 when left out. `noExpiry: true` makes a token that never expires and cannot be combined with `expiresInDays` (400). A token that never expires is a standing key that works until someone revokes it, so make one only on purpose. The listings say `neverExpires`, and so does the audit event of its creation.
- **Sensitive scope.** A token passes a check for a sensitive permission only through an explicit list, `sensitivePermissions`, of permission keys such as `sensitive:read:medical`. That needs the sensitive switch on (422 `api-sensitive-tokens-disabled`); each key must be a permission that exposes sensitive data (422 `not-a-sensitive-permission`, with the places in the list); the person must hold each one where the token works (422 `token-exceeds-own-access`, with the keys); and a `read` token may list only read permissions (422 `token-read-only-scope`, with the places in the list). The checks are made again each time the token is used: the key must still be listed, the switch must still be on, and the owner must still hold the permission at that moment. A token without the scope is refused on every sensitive permission even when its owner holds it. Every sensitive read through a token writes the `sensitive.read` audit event marked with the token's id.
- **Read and write.** Every permission is classed `read` or `write` in code (`access` on its definition in the `PERMISSION_LISTS` registry; a permission that does both counts as `write`, and a key that ends in `:read` but is classed `write` needs a stated reason). A `read` token passes only read permissions, and only on a route that says `tokenAccess: 'read'`; on a route that changes data it is a 403 `token-read-only`. The class is not stored in the database and is not in `GET /meta`.
- **Using one.** `Authorization: Bearer <token>`. No `Origin` is needed: a token is not a cookie, so there is nothing for another site to borrow. A request that sends a session cookie as well is a 400 `ambiguous-credentials`. A `Bearer` value that does not start with `osfpm_pat_` is not ours and is left alone, as another scheme is, so a reverse proxy that forwards its own `Authorization: Bearer` header does not break the browser. A token works only if all of these hold: it is not revoked and has not expired; both switches allow it; its owner's account is active, and so is the owner's membership of the token's organisation; its owner still holds `api:tokens` there; and, on a route under `/organisations/:organisationId`, the path names the token's own organisation. **Anything else is the same 401 `invalid-token`, with one body.** The cause is in the audit trail (`auth.api-token-auth-failed`, a reason code and never any part of the token). A failed attempt counts against the strict limit per address (10 a minute, the bucket the sign-in routes share), and once the address is over it a failing token is a 429 and is not written to the audit trail. A token that works is never held up by that limit and is not counted in it; it has the limit of a session, 120 a minute, counted per token. `last_used_at` is written at most once a minute.
- **Routes refuse tokens unless they say `tokenAccess`.** `config: { tokenAccess: 'read' }` (a safe method only: `GET`, `HEAD` or `OPTIONS`) or `'write'` opts a route in, and a token on any other route is a 403 `token-not-accepted` (a route that is `auth: 'none'` and says nothing ignores the header). Today `GET /meta` and `GET /organisations/:organisationId/members` accept a token, both as `read`. **The credential and account routes (`/auth/*`, setup, accepting an invite, `access-reset`), making invites and reset links, token management and the switches never do**, and a test walks every registered route and fails if one of them does. A token cannot sign in, change a way to sign in, bring a person into the organisation, make or revoke tokens, or change the switches.
- **Narrowing.** A token's request runs as its owner, narrowed by the token. It works only in its own organisation (an id in the path may be written in upper case, as for a session: the plugin puts the organisation and project ids of a token's request in lower case before anything compares them). A project token passes only checks for that project and none at organisation level. A `read` token passes no write permission. And it never passes more than its owner holds at that moment, so a role taken from the owner narrows the token at once.
- **Audit.** `auth.api-token-created` (the token, its owner, the project, the access, the sensitive keys, the expiry or "never" and the prefix), `auth.api-token-revoked` (the reason, `manual`, `switch-off` or `access-reset`, and by whom), `auth.api-token-switch-changed` (which switch, on or off, and how many tokens it revoked), `auth.api-token-auth-failed` (a reason code), and **`api.call`, one event for every request a token made, written after the response**: the token, its owner, the organisation, the method, the route pattern (not the URL) and the status, and never a query, a body, a header or the token. No log line, audit event, change event or error body holds a token, a hash or anything of a token beyond the stored prefix; the log formatter also masks `osfpm_pat_…` wherever it appears in text (see Logging).
- **Account events.** Using an admin reset link revokes every live token of the person (reason `access-reset`) and counts them in its event. A membership that stops being active makes its tokens fail at once; revoking them with the reason `membership-ended` comes with member management (P-04b). The worker's transient cleanup deletes revoked and expired tokens; the audit trail is the record.
- **Races.** Making a token takes the organisation's change counter before it reads the switches (the lock-order rule in CLAUDE.md), so it cannot race a switch being turned off: the token is made and then revoked, or it is refused. Two revokes of one token end with one revocation and a 404 for the other. PostgreSQL-only tests show both.

What is not here: OAuth apps, webhooks, key-signed requests, settings inherited from a parent organisation (P-04), removing a member and the server's administration tool.

## My delivery preferences

A person tells OSFPM how they want to receive information (decision D-69, P-02l2): plain-text or HTML email, a standard, easy-read or large-print document, a text size, a channel, each message as it comes or a daily digest, and quiet hours. These are **ordinary settings, not sensitive data**, so nobody has to disclose anything to get an accessible format. The rules are in the core (`packages/core/src/preferences/`); the routes are in `src/preferences/`.

- **Two routes, self-service.** `GET /api/v1/me/preferences` answers `{ stored, effective }`: what the signed-in person chose (only those fields) and what applies, with the defaults filled in (`html`, `standard`, `default`, `email`, `instant` and no quiet hours). `PUT` takes the same fields, every one optional, replaces what the person chose (a field left out is cleared, `{}` clears them all) and answers the same shape. They act only on the signed-in person's own preferences, so there is no permission to lack.
- **Session only.** The routes do not say `tokenAccess`, so a personal API token is a 403 `token-not-accepted`, and they do not say `allowedInRecovery`, so a recovery session, which may only secure the account, is a 403 `account-recovery-required`. No session is a 401, and a `PUT` with a cookie needs the right `Origin` like every route that changes data. The answers say `cache-control: no-store`.
- **A strict body.** A field the schema does not know, or a value it does not allow, is a 400 `validation-failed` that lists where (`body` and the field's path, such as `quietHours.end`) and never the value or the name the caller chose. Quiet hours are `HH:MM` in the person's own time zone, may cross midnight (22:00 to 07:00), and may not start and end at the same time.
- **Shown to few.** They are not sensitive, but only the person, staff who hold `people:edit` (for a person with no account) and system code (`effectivePreferences`) read them, as a courtesy: `easy-read` can hint at something a person has not chosen to share. There is no route for another person's preferences: staff set those of a person with no account through the core service. The permissions `people:read`, `people:edit`, `companies:read`, `companies:edit`, `locations:read` and `locations:edit` are declared with them (organisation-level, none sensitive), and the start-up top-up gives all six to the Administrator role.
- **Audit.** A save writes `preferences.saved` (action `create` the first time, `update` after) with the user and the names of the fields that changed, and never a value. No log line, audit event or error body holds a choice.
- **When the account goes.** Deleting an account erases its preferences (`endAccountAccessSharing` in the core; the account-deletion service that will call it does not exist yet).

What is not here: a route for another person's preferences, sending anything in the chosen format (the email module comes later, and an urgent message may override quiet hours and the digest, which that module decides) and the call sheets.

## Server keys

Each install has two kinds of key, kept **outside the database**, in the directory `OSFPM_KEYS_DIR` (spec, section Cryptography and keys). The core's `src/keys/` loads and checks them; `bindServerKeys` binds them to the database at start-up.

| File                    | What it is                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| `server-identity.pem`   | The server's Ed25519 private key (PKCS #8 PEM). Its public half is published and stored on the installation |
| `data-keys/<keyId>.key` | A data key: 32 random bytes in base64. The key id is a UUIDv7. Several may exist                            |
| `data-keys/current`     | The key id of the data key that encrypts new values                                                         |

With PGlite the directory defaults to `<OSFPM_DATA_DIR>/keys`, beside the data. With PostgreSQL `OSFPM_KEYS_DIR` is **required**, so the database and its keys are never quietly in different places. The server makes any file that is missing, as the database allows (below), with mode 0600 in directories of mode 0700. A file that is there is never changed.

**Back up the key directory with the database.** The keys are secrets: restrict who can read the backup as you restrict the database's. On a POSIX system the server refuses to start if a key file can be read by the group or others, and says which file; fix it with `chmod 600` (a secret mounted by a container platform needs a mode of 0400 or 0600). On Windows the mode bits say nothing about access, so that check is skipped there: protect the folder with its access rules. Servers that share one database must share one key directory.

**What the keys do.**

- **The identity key** identifies this server. The first time the server starts with a key, the public key (the raw 32 bytes, base64url) is stored in `installation.server_public_key` and one `auth.server-key-bound` event is written. After that the database remembers it: a key directory with another key, or with no `server-identity.pem`, **stops the server** with a message that says the directory does not belong to this database and to restore the matching keys from backup. The server never replaces the stored key and never makes a new identity for a database that has one, so a swapped or empty volume cannot quietly change who the server is. The one thing that replaces it is the admin command `new-identity`, on the operator's confirmation, for an install whose identity file is lost (see [Admin command line](#admin-command-line)). The public key is published at `GET /.well-known/osfpm/server-key` (see [Routes](#routes)). Federation and signing come later and will use it.
- **The data keys** encrypt an authenticator-app (TOTP) secret before it is stored. A stored secret is `v1.<keyId>.<nonce>.<ciphertext and tag>` (AES-256-GCM, a new nonce each time), carries the id of its key, and is bound to its row, so it does not open if it is copied to another user's row. A database dump alone no longer gives anyone a user's codes. Secrets stored as plain base32 before this was built are encrypted in place at the next start, with one `auth.totp-secrets-encrypted` event that holds the count. Nothing else is encrypted by these keys yet; the reserved `key_id` columns are left alone. `rotate-data-key` (see [Admin command line](#admin-command-line)) adds a data key and re-seals the secrets under it: the server holds several data keys and opens a value with the key its text names.

**If the keys are gone.** The server will not guess. With an authenticator secret in the database and no data keys (the `data-keys` folder is missing, or `current` names a file that is not there), start-up stops with a message that names `OSFPM_KEYS_DIR` and the backup. With no encrypted secret in the database, missing data keys are simply made. A secret that is in the database but cannot be opened (its key is not in the directory, or it was copied from another row) is treated as no valid authenticator: sign-in answers the same 401 as for a wrong code, and the audit event says `totp-undecryptable`, which is not counted as a wrong guess. **What losing the data keys costs is the authenticator codes and nothing else:** the people who had set one up sign in with a passkey or a recovery code and set up an authenticator app again. **Restore the directory from your backup.** With no backup, `accept-data-key-loss` accepts that loss and makes a fresh data key (see [Admin command line](#admin-command-line)); the people whose secrets cannot be opened sign in with a passkey, a recovery code or a reset link and set up their authenticator app again, because setting up replaces a confirmed secret that the server cannot open (a password alone cannot get past it). Losing `server-identity.pem` stops the server in the same way, and the same backup restores it; with no backup, `new-identity --confirm-new-identity` makes a new identity, and the identity the server publishes changes.

**Nothing prints a key.** A key, a secret or a key file's contents is never in the database, a log, an error, an audit event, a change event, a response or `/meta`; only the public key and its fingerprint are public. The audit events hold a count, a fingerprint, or a fixed reason. A start-up refusal prints a fixed message that names the path of a key file at most, and the logger masks a key named like key material or a secret, a private key written as PEM text, and the names of the key files (see [Logging](#logging)).

## Admin command line

System administration in this phase is a command line (decision D-64). Shell access to the server is the trust boundary, because no installation-level web role exists yet, and there is no web route for any of it. Run it from the repository root:

```sh
pnpm --filter @osfpm/api admin <command> [options]
```

It is the development form, over `tsx` like `start`; a real `osfpm` binary comes with the production image (P-07). pnpm writes its own `$ tsx …` line to standard error, so standard output stays the report; a script that reads `--json` can also run `pnpm --silent …`.

It reads **the same environment as the server** (`DATABASE_URL` or `OSFPM_DATA_DIR`, `OSFPM_KEYS_DIR`, the rest of [Configuration](#configuration)) through the same `loadConfig`, so an invalid setting stops it with the same fixed message, which names variables and never a value. `OSFPM_PUBLIC_URL` is required, as it is for the server, although only `doctor` looks at it.

| Command                               | What it does                                                                                                                                                                                                                      | Server running?                         |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `info`                                | Prints what the installation holds: counts, the installation's id, fingerprints. No name and no address. `--json` for a script                                                                                                    | PostgreSQL: may be. PGlite: **stop it** |
| `doctor`                              | Runs eleven checks and prints `ok`, `warn`, `fail` or `skipped` for each. Exits 1 when a check fails. `--json` for a script                                                                                                       | PostgreSQL: may be. PGlite: **stop it** |
| `rotate-data-key`                     | Adds a new data key, makes it the current one and re-seals every authenticator secret that an older key sealed. Old key files are kept                                                                                            | **Stop every server**                   |
| `accept-data-key-loss`                | For an install whose data keys are gone (start-up refuses with `data-keys-missing`): makes a fresh data key and makes it current. Changes no row. Changes nothing when a usable current key exists                                | **Stop every server**                   |
| `new-identity --confirm-new-identity` | For an install whose identity key file is lost and cannot be restored: makes a new identity key and stores its public key. The server's published identity changes. Does nothing without the flag, and refuses when a file exists | **Stop every server**                   |

**Exit codes.** `0` done, `1` the command was refused or failed (and `doctor` when a check fails), `2` the arguments were wrong. The report is on standard output, as text, or as JSON with `--json` (`info` and `doctor` only). Errors, warnings, refusals and the usage after a mistake are on standard error. `--help` prints the usage. **pnpm's `--filter` form reports every failure as exit code 1**, whatever the command answered, and adds an `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL` line of its own to standard error; `pnpm --dir packages/api admin <command>` passes the command's own code through, which a script that tells 1 from 2 needs.

**Every command goes through the same guards, in this order.** The settings load. The database is marked as in use for the kind of command it is (below). The database answers. **No migration is pending**: the command line never migrates, so a database with pending migrations is refused with a message that says to start the server once (which applies them, unless `OSFPM_AUTO_MIGRATE` is `false`), stop it, and run the command again. It never makes a PGlite database either: a data directory with none in it is refused, so a mistyped path does not make an empty one. `doctor` is the one command that reports these instead of refusing: it exists to say what is wrong.

**Nothing secret is printed, logged or audited.** Not a key, a key id, a secret, a token, an email address or the database URL: only counts, the installation's id, fingerprints, booleans, paths of key files and dates. A failure prints the error's class name and its short system code, such as `ECONNREFUSED`, and nothing else, because a driver's message can hold the connection's address or a password. The errors written for the operator (an invalid setting, a database in use, a key file that cannot be used) have fixed text.

**Every command that reaches the database writes one audit event**, actor `system`, in its own transaction. `info` and `doctor` write `admin.command-run` (the command, how it ended, counts). The key commands write their own: `auth.data-key-rotated` (the counts re-sealed and not openable), `auth.data-key-loss-accepted` (the count that cannot be opened) and `auth.server-identity-replaced` (the old and the new fingerprint). A key command that found nothing to do, or was refused for a reason about the installation, writes `admin.command-run` with the outcome `nothing-to-do` or `refused`. A command refused before the database (a usage error, a missing `--confirm-new-identity`, a database in use, pending migrations) writes nothing. If `doctor` cannot reach the database it cannot audit, and says so in its output.

### Why the commands that change keys need every server stopped

A running server holds the data keys and the identity key **in memory**, loaded at start-up. A command that changes what is on disk would leave it out of step: a server that does not know the new current key seals new secrets with the old one, and one that never saw a new identity keeps publishing the old. So these commands refuse while any server uses the database, and a server waits for them. One helper decides what that means for each driver (`markDatabaseInUse`, in the core's `src/db/in-use.ts`).

- **PostgreSQL.** Every server takes a **shared** session-level advisory lock (`IN_USE_LOCK_KEY`, next to the migration lock's key) on one connection that it holds for its whole life, and gives it back when it shuts down. A command that needs every server stopped takes the **exclusive** lock for its whole run, with `pg_try_advisory_lock`, which never waits: if a server holds the shared lock it is refused at once with "A server is using this database. Stop every server, run the command, then start them again." (another admin command that is running gives the same answer). A server takes its lock with `pg_try_advisory_lock_shared` as the first step of every attempt of its start-up retry loop, so a command that is running only makes it "not ready yet": one warning line per attempt, the wait doubling up to thirty seconds as for an unreachable database, and a stop signal ends the wait. `info` and `doctor` take no lock and run beside servers. **Holding one connection leaves the server's pool one connection fewer** (the `pg` pool defaults to ten, so nine are left for its work); a command uses its own pool, one connection for the lock and one for its work. If a server's connection is lost (the database restarted), the lock goes with it, the server logs one line saying so, and a command could run beside it until it restarts: restart the servers after restarting the database, before a key command.
- **PGlite.** PGlite itself does **not** refuse a second process on a data directory: tried with 0.5.16, the second process opened and queried it while the first held it open, with no error. So every command takes a lock file, `osfpm.lock` in `OSFPM_DATA_DIR`, before it opens the directory, `info` and `doctor` too, because two processes must never open one PGlite directory. It is made with `wx` and holds the process's number. A server takes it at start and removes it on shutdown, and one that finds it held refuses to start. A file whose process is no longer running is a leftover of a crash and is replaced, and so is one that holds this process's own number without this process having made it (a killed container leaves its file, and the next container's first process has the same number). If nothing is running and a command still reports a process, delete the lock file it names. **The server must be stopped for any command on a PGlite install.** A `memory://` data directory has nothing to lock.

An offline command also takes the `installation` row `FOR UPDATE` first, inside its transaction, as start-up's key step does, so two commands, or a command and a server that slipped past the lock, take turns.

### The key commands

**`rotate-data-key`** adds a new data key and makes it the current one: the key file first (mode 0600, never over a file that is there), then `data-keys/current` in one step, so the files are never half done. **Old key files are never deleted; keep them**, because an older backup of the database still needs them, and back the key directory up again after a rotation. Then, in one transaction, it re-seals every authenticator secret that an older key sealed and a key in the directory still opens, under the new key. A secret that no key opens is left exactly as it is and counted. It prints the two counts. If the transaction fails after the key files were written, `current` already names the new key, which is harmless: the ring the server builds from the directory still holds every old key, so every secret still opens, and running the command again finishes the job.

**`accept-data-key-loss`** is for the install that start-up refuses with `data-keys-missing`: the database holds sealed authenticator secrets and the data keys are gone. With no usable current key it makes a fresh data key and makes it current, changes no row, and says how many sealed secrets can no longer be opened. Those people sign in another way (a passkey, a recovery code or a reset link) and set up their authenticator app again: setting up replaces a confirmed secret that the server cannot open, which is safe because they already hold a session, while a password alone cannot get past a secret that cannot be opened. With a usable current key it changes nothing, prints how many secrets cannot be opened, and exits 0. It never reads, makes or changes the identity file. **Restoring the key directory from a backup is always better**; this command is for when there is none.

**`new-identity --confirm-new-identity`** is for the install whose `server-identity.pem` is lost and cannot be restored (start-up refuses with `identity-missing`). The identity the server publishes cannot be undone, so it does nothing, and does not open the database, without the flag. With it, and after its checks have passed, it prints a warning on standard error that the published identity will change (with the old fingerprint), makes a new Ed25519 key, stores its public key on the installation in place of the old one, writes the event with both fingerprints, and writes the private key file last, so a failure to write it takes the database change back. **It refuses when anything is at the path of the identity file**, whether it matches the stored key or not: a file that does not match means a wrong volume, and the command never deletes or overwrites a key file. The message tells the operator to move the file away themselves if they really mean to replace it. It also refuses when the installation has stored no key yet (start-up binds the first one) and when the server has never started.

### Recovery: a key directory lost, with no backup

1. **Stop every server**, and check that `OSFPM_KEYS_DIR` points where it should. An empty or wrong volume is the usual cause, and restoring the right directory beats everything below.
2. Run `pnpm --filter @osfpm/api admin doctor`. It says which part is missing: `identity` fails when the identity file is gone, `data-keys` when sealed secrets need data keys that are gone.
3. **Data keys gone:** `pnpm --filter @osfpm/api admin accept-data-key-loss`. The cost is the authenticator codes of the people who had set one up, and nothing else.
4. **Identity file gone:** `pnpm --filter @osfpm/api admin new-identity --confirm-new-identity`. The cost is that the server's published identity changes.
5. A directory that lost **both** needs both commands, **in either order**: each makes only its own part, and start-up says which one is still missing.
6. Start the server. People whose authenticator secret was lost sign in with a passkey, a recovery code or a reset link, and set up their authenticator app again.
7. **Back up the new key directory with the database**, now.

**The public URL is also the passkey's relying party.** The host name of `OSFPM_PUBLIC_URL` is the id a browser ties every passkey to, and its origin is the only origin a passkey ceremony may happen on. **Changing the host makes every existing passkey unusable**: the people who used one have to sign in another way (a password or a recovery code) and add their passkeys again. Changing only the scheme or the port does not. An IP address cannot be a relying party id, so passkeys need a host name; use `http://localhost:<port>` for development, and not `http://127.0.0.1`.

## Authentication

A signed-in user is a session cookie, `__Host-osfpm_session`. The auth plugin (`src/auth/plugin.ts`) runs on every request before the body is read: it reads the cookie, asks the core's `validateSession`, and puts the result on `request.auth` with a core `WriteContext` whose actor is the user (`request.auth.context`). A cookie that is invalid, expired or revoked, or belongs to a disabled user, is treated as no session and the response clears it.

**The `auth` route option.** Every route declares how it treats a session, in its route `config`:

| `config.auth`          | Meaning                                                                                                                                                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'required'` (default) | A valid session, or a 401. A route that says nothing is `required`, and so is any value the plugin does not know                                                                                                           |
| `'optional'`           | A valid session is used if there is one. None is not an error, and a cookie that is no good counts as none (`POST /invites/accept` checks for one itself and answers 401)                                                  |
| `'none'`               | The route does not use the session. Cookies are ignored: no lookup, no clearing, no origin check of a cookie (a route that makes a session says `requireOrigin` instead, see below). Health, meta, OpenAPI, sign-in, setup |

A `required` route without a valid session answers **401** `authentication-required`, with the same text whatever the reason: no cookie, an unknown token, an expired or revoked session, a disabled user. A response never says which. The plugin does not touch an unknown route, which is a 404.

**Personal API tokens.** A route also says whether a personal API token may call it (`config.tokenAccess`, see Personal API tokens). A route that says nothing refuses tokens (one that is `auth: 'none'` uses no credential and does not read the header), and `request.auth` is a session only. The handler of a route that accepts tokens reads who is calling with `requireCaller`, which gives the user and the credential to pass to the services.

**The cross-site check (CSRF).** A `POST`, `PUT`, `PATCH` or `DELETE` that carries a session cookie must have an `Origin` header equal to the origin of `OSFPM_PUBLIC_URL`, written as a browser writes it (scheme, host and port, no path: the setting has none either). A missing or different `Origin` is a **403** `origin-mismatch`. It is checked before the session is looked up, so a cross-site caller learns nothing about whether its cookie was good. A request with no session cookie is not checked, since there is nothing to borrow; a request with a personal API token (`Authorization: Bearer`, see Personal API tokens) has no cookie and is authenticated another way. Safe methods are not checked.

**Routes that make a session** are the exception: they say `config: { requireOrigin: true }`, and a `POST` to one needs the right `Origin` **whether or not it carries a cookie**, and whatever the route's `auth` mode. A page on another site has no cookie to borrow, but without this it could make a visitor's browser sign in as someone else, or use up the setup code's attempts. They are `POST /auth/login/password`, `/auth/login/totp`, `/auth/login/recovery`, `/auth/login/passkey/verify`, `POST /setup`, `POST /setup/check` and `POST /access-reset` (with `POST /access-reset/inspect`, its first step). A missing, different or malformed `Origin` (another site, another port, `http`, a trailing slash, `null`) is a 403 `origin-mismatch`, decided right after the strict limit, so a refused request is counted against it and spends no code, challenge or password attempt. `POST /auth/login/passkey/options` makes no session, only a challenge, and takes any `Origin`. A route that makes a session asks `assertOriginRequired` first, so a new one that forgets the option fails its first test with a 500. A browser needs to do nothing; a script or a command-line client must send `Origin` with the origin of `OSFPM_PUBLIC_URL`.

**The recovery scope.** A session a recovery code or an admin reset link opens (and one that first-run setup or an invite opens without a password) has the scope `recovery`, not `full`. It may only call a route that says `config: { allowedInRecovery: true }`: `me`, `logout`, the five routes that set a new way to sign in, the two that add a passkey and the two that list and revoke passkeys, so a person whose device was lost can remove its passkey (see Routes). Any other route, whatever its `auth` mode but `none`, answers **403** `account-recovery-required`: so does the route that renames a passkey. The answer says what the session is for, the same for every way it was opened (a recovery code, first-run setup, an invite or a reset link): "This session can only be used to secure the account: set a password or add a passkey." A route is closed to such a session unless it says otherwise, so a new route cannot be open to it by accident. It is checked after the cross-site check and the limit per session, so a forged request learns nothing about the scope. Setting a new password, confirming an authenticator app or adding a passkey makes the session `full`.

**The cookie.** When a login route sets it: `__Host-` prefix, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`, and `Expires` set to the session's absolute expiry (`setSessionCookie` in `src/auth/cookie.ts`). Logout and an invalid cookie clear it with the same attributes, which a `__Host-` cookie needs to be replaced. A browser that does not treat `http://localhost` as a secure context will not keep it there; Chrome and Firefox do. The raw token is never logged, returned after it is set, or stored: the log scrubber masks the cookie name as a key and as text.

**Rate limits.** There are three, for three different jobs. Past any of them, the answer is **429** `rate-limited` with `Retry-After` in seconds.

- **A coarse limit on every route** (`ADDRESS_RATE_LIMIT` in `src/auth/rate-limit.ts`): at most 300 requests per minute **per address**, counted together across every route except `/health` and `/health/ready`, which say `exemptFromAddressRateLimit` so that a supervisor can always probe, even a busy address. A request for a path that is no route counts too: it still costs a request and a log line. It is counted before anything else, **before the session is looked up**, so a flood with no session, or a wrong one, costs the server a count and no database query. It is far above what a client needs; the other two shape use. While the server is still starting, a request is a 503 `starting` first and is not counted.
- **For routes that check a secret** (`config: { authRateLimit: true }`): at most 10 requests per minute **per address** (`AUTH_RATE_LIMIT` in `src/auth/rate-limit.ts`), counted together across every such route. This one is for guessing: the five login routes, the two setup routes, the two invite routes (`POST /invites/inspect` and `/accept`) and the two reset routes (`POST /access-reset/inspect` and `POST /access-reset`) set it (they all count together). A personal API token that fails counts in the same bucket, and one that works does not (see Personal API tokens). It is counted right after the coarse limit and before the session is looked up, so a caller with no session, a wrong one or a foreign `Origin` is limited too.
- **For routes a signed-in client uses as it goes** (`config: { sessionRateLimit: true }`): at most 120 requests per minute **per session** (`SESSION_RATE_LIMIT`), counted together across those routes, whatever the address. `me`, `sessions`, `logout`, the five account routes and the five passkey routes set it. It is counted once the session is known and the `Origin` has passed, so a forged request does not spend the session's own. A request with no valid session is not counted: it is a 401 and has no session to count against.

The counts are kept in this process's memory (`@fastify/rate-limit`'s local store). Several API instances each keep their own, so a limit becomes the limit times the number of instances until they share a store.

**Behind a reverse proxy,** set `OSFPM_TRUSTED_PROXIES`. By default the server believes no header and takes the address of the connection, so every caller behind a proxy is the proxy, and the limits per address are one limit for all of them. With the proxies listed, the server reads `X-Forwarded-For` from a connection that comes from one of them, takes the first address from the right that is not a proxy, and ignores anything a client wrote to the left of it. A connection from anywhere else is never believed, so a caller cannot change its address by sending the header. List only the proxies in front of the server. A range of everything (`/0`) is refused, because it would believe any caller.

While first-run setup is to do, only the health routes, `meta`, `openapi.json` and the two setup routes answer; every other route is a 503 `setup-required` (see First run).

The session routes, the account routes and the passkey routes (but for the two sign-in routes) are self-service: each acts on the signed-in user's own account, so there is no permission to lack. Without a session the answer is 401. The 403s are the cross-site check, `account-recovery-required` (a recovery session on a route that is closed to it) and `current-password-incorrect` (a change that needs the current password, which was missing, wrong or throttled: one answer for all three). The only secrets in any response are the ones shown once, in an uncacheable response and never again: an authenticator secret and its address, a challenge, recovery codes, and a session token, which goes only into the cookie.

**Every failed sign-in step answers the same 401 `sign-in-failed`, with one body.** An address no one has, an account with no password, a wrong password, authenticator code or recovery code, a challenge that is unknown, used, over time or out of attempts, a passkey that is unknown, revoked or does not verify, a signature counter that went back, a disabled user and an account closed for a while after five wrong guesses in fifteen minutes cannot be told apart from the answer. A request that is not shaped right stays a 400. The cause is in the audit trail only, as a reason class and never a submitted value. The throttle and the other rules are in `packages/core/src/auth/README.md` and `src/auth/README.md`.

Every response carries an `X-Request-Id` header: a UUIDv7 made by the server. An ID sent by the caller is ignored.

## Logging

One line per request, written when the response is sent: method, route pattern, status code, duration and request ID. A line never holds a URL, a query, a path parameter, a header or a body, so a `token` in a query string or an `authorization` header cannot reach it. Errors are logged by class name and request ID, never by message. If a handler writes a line by hand, two independent layers mask credentials. A scrubbing formatter masks every key named like a `token`, `authorization`, `cookie`, `set-cookie` and the session cookie `__Host-osfpm_session`, at any depth. The formatter also masks a token-named query parameter, the session cookie and a personal API token (`osfpm_pat_…`) inside a string, and logs a request or reply object as its class name only. Under it, fixed redact paths mask the three credential headers. A line never takes its message from an error, because Fastify's own warnings quote the whole URL there. These layers are a safety net, not permission to log objects: the rule in CLAUDE.md (Code rules) is to log the known keys `req`, `res` and `err`, or plain scalar fields, and never whole objects or request data (Privacy rule).

A key named like key material or a secret (`privateKey`, `identityKey`, `dataKeys`, `keyMaterial`, `secret`) is masked, a string that holds a private key as PEM text is masked whole, and the name of the identity key file and a path into `data-keys/` are masked wherever a string names them (see [Server keys](#server-keys)).

A refused request is a warning with the error's class name. A start-up failure is one `fatal` line with no request in it. Neither holds an address, a cookie or a token.

The caller of `buildApp` chooses only the level and the destination. What a line may hold is fixed in `src/logging.ts`.

## Add a route plugin

Each area of the API is a Fastify plugin. A module adds its own and registers it in `buildApp`; it never edits another area's plugin.

1. Create `src/routes/<area>.ts` (or a folder). Validate every input with a Zod schema and describe each response with one. The OpenAPI document is generated from them. **Declare `auth`**: a route that says nothing is `required`, which is what most routes want, and a route that must work without a session says `config: { auth: 'none' }`. A route that checks a secret sets `authRateLimit: true` (10 a minute per address), and a route a signed-in client uses as it goes sets `sessionRateLimit: true` (120 a minute per session). A session a recovery code opened is refused on a route unless it says `allowedInRecovery: true`, which only the routes that set a new way to sign in say. A route that must answer before first-run setup is complete says `availableBeforeSetup: true`; a route that says nothing answers 503 `setup-required` until the first administrator exists. **A route refuses personal API tokens unless it says `tokenAccess`**: `'read'` for a route that only reads (a safe method) or `'write'`. Say it only when every service the route calls takes the credential (`requireCaller` gives it with the user) and passes it to its permission checks, because that is what narrows the token to its organisation, project, access and sensitive scope. A route that signs people in, secures an account, hands out access, or manages tokens or their switches never says it.

   ```ts
   import type { FastifyPluginAsyncZod } from 'fastify-type-provider-zod';
   import { z } from 'zod';
   import { requireAuthenticated } from '../auth/plugin.js';

   export const exampleRoutes: FastifyPluginAsyncZod = (app) => {
     app.get(
       '/examples/:id',
       {
         // No `auth`, so the route is `required`: the plugin has already answered
         // 401 if there is no valid session, and `requireAuthenticated` cannot fail.
         schema: {
           params: z.object({ id: z.uuid() }),
           response: { 200: z.object({ id: z.uuid(), name: z.string() }) },
         },
       },
       async (request) => {
         const { context } = requireAuthenticated(request);
         // `findExample` stands in for a core service, which takes app.db.db and
         // who is asking. Do not catch its errors: let them go, and the error
         // table maps them.
         return findExample(app.db.db, context, request.params.id);
       },
     );
     return Promise.resolve();
   };
   ```

   A route that changes data and is `required` or `optional` gets the cross-site check from the plugin, with nothing to add.

2. Add one line to `buildApp` in `src/app.ts`, next to the others: `void app.register(exampleRoutes, { prefix: API_PREFIX });`

3. If the module defines error classes, add a row for each to `PROBLEM_TABLE` in `src/errors.ts` (or an entry with a reason to `INTERNAL_ERRORS`). A row either states its own `detail` or passes on the error's message, and only an error whose documentation says its message holds no ids and no values may do that.

4. Test it with `app.inject()` (see below). Tests that register their own routes on a test app must say `config: { auth: 'none' }` on each, or the default `required` answers 401. CLAUDE.md requires, for every permission-protected endpoint, a test that it answers 403 without access and returns no sensitive fields without `sensitive:read`. A self-service endpoint, which acts only on the signed-in user's own account and has no permission to lack, tests instead that it answers 401 without a session, 403 `origin-mismatch` for a foreign `Origin` on a request that changes data, and 403 `account-recovery-required` for a recovery session unless the route says `allowedInRecovery`. A public endpoint (`auth: 'none'`) tests that all its failures give the identical answer and that its rate limit applies. A route that says `tokenAccess` also tests that a token for another organisation gets the 401 `invalid-token`, that a token whose owner lacks the permission gets the 403 the owner would, and that a project token and a `read` token are narrowed as they should be; and it is added to the list in `src/api-tokens/token-access-routes.test.ts`, which pins the routes that accept a token.

Import core code by path, for example `@osfpm/core/src/db/write.js`: the core has no build step yet and its package index exports only a placeholder.

## Tests

From the repository root:

```sh
pnpm test packages/api
```

They use `app.inject()`, so no port is opened, except `src/server.test.ts`, which starts the server on a free port, and `src/admin/main.test.ts`, which runs the admin command line as a process. They run on PGlite always and on PostgreSQL as well when `DATABASE_URL` is set (see the main `README.md`). `src/jsdoc.test.ts` in the core package also fails when an export in this package has no JSDoc.

Most tests make a session with the core's `createSession`, on an app that is told first-run setup is complete (`createTestApp`; pass `setupComplete: false` and give the database the state to test the gate or the setup routes). The tests of first-run setup are in `src/setup/`: `first-run-startup.test.ts` (the installation row and the printed code), `gate.test.ts`, `setup-routes.test.ts`, `setup-secrets.test.ts` and `setup-race.test.ts` (PostgreSQL only: two requests held on the installation row lock). the tests of the login routes sign in through them. The reset link routes are tested in `src/access-reset/access-reset-routes.test.ts`. The preferences routes are tested in `src/preferences/preferences-routes.test.ts`. The personal API token routes are tested in `src/api-tokens/`, and the plugin's part in them in `src/auth/token-plugin.test.ts`. The passkey tests answer the browser's WebAuthn calls with the core's software authenticator (`softwareAuthenticator` in `packages/core/src/auth/test-support.ts`), so the library's real verification runs. A test that sends many requests gives each its own `remoteAddress`, so the rate limits measure only what the test means them to.

Test data is the fictional production _The Last Withdrawal_ or invented values, never real people's data.
