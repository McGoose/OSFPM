# auth (API)

How a person signs in to the API, and how the API knows who a request is from (spec card SC-10, decision D-56). The services that check a password, a code or a challenge are in the core (`packages/core/src/auth/`); this folder is the HTTP side: the session cookie, the plugin that reads it, the limits, and the routes.

**Entry points**

- `plugin.ts`: `authPlugin`, which turns the session cookie into `request.auth` on every request, applies the three rate limits and the cross-site check, and keeps a recovery session to the routes that allow it. `requireAuthenticated` reads the acting user in a handler, and `assertOriginRequired` is what a route that makes a session asks first.
- `cookie.ts`: the `__Host-osfpm_session` cookie, `setSessionCookie` and `clearSessionCookie`.
- `rate-limit.ts`: `ADDRESS_RATE_LIMIT`, `AUTH_RATE_LIMIT` and `SESSION_RATE_LIMIT`, in one place.
- `login-routes.ts`: `loginRoutes`, the five sign-in routes under `/api/v1/auth/login`: `password`, `totp`, `recovery`, `passkey/options` and `passkey/verify`. It is registered with the relying party.
- `account-routes.ts`: `accountRoutes`, the five routes a signed-in user secures the account with: `PUT /password`, `POST /totp/enrol`, `POST /totp/confirm`, `DELETE /totp` and `POST /recovery-codes`.
- `passkey-routes.ts`: `passkeyRoutes`, the five routes a signed-in user manages passkeys with: `POST /passkeys/register/options`, `POST /passkeys/register/verify`, `GET /passkeys`, `PATCH /passkeys/:id` and `DELETE /passkeys/:id`. It is registered with the relying party.
- `passkey-schemas.ts`: the Zod schemas of the WebAuthn JSON forms (the options a browser is given and the responses it sends back) and of a passkey as a response shows it.

The routes for a user's own sessions (`me`, `sessions`, `logout`) are in `src/routes/auth.ts`. First-run setup (`POST /setup/check` and `POST /setup`) is in `src/setup/`: the session it makes has method `setup`, and scope `recovery` when no password was given, so it follows the recovery-scope rule below. Admin reset links are in `src/access-reset/`: the session they make has method `reset` and the recovery scope too. The full route table is in `packages/api/README.md`.

**How it works**

- **A sign-in step is one transaction.** The route opens it, calls the core, and on success makes the session in the same transaction, so the user row lock the core takes is held until the session exists. The core returns a failure instead of throwing it, so the transaction commits and the audit event of the failure is kept; the route throws after it.
- **Every failure is the same answer.** An address no one has, an account with no password, a wrong password, authenticator code or recovery code, a challenge that is unknown, used, over time or out of attempts, a disabled or deleted user, and an account the throttle has closed all answer **401** `sign-in-failed`, with one body. Nothing in it says which part failed or whether an address has an account (CLAUDE.md, Code rules). The cause is in the audit trail only, as a reason class and never a submitted value. A request that is not shaped right stays a 400.
- **A password sign-in has one or two steps.** `POST /login/password` makes a session (method `password`) and sets the cookie, unless the user has a confirmed authenticator app. Then it makes no session and answers `{ next: "totp", challenge }`, and `POST /login/totp` with the challenge and a code makes the session (method `password+totp`).
- **A recovery sign-in opens a limited session.** `POST /login/recovery` uses a recovery code up, ends every other session of the user (the core does it, reason `recovery-used`), and makes a session of method `recovery`, scope `recovery`, and answers `mustSecureAccount: true`. That session may call only a route that says `config.allowedInRecovery` (`me`, `logout`, the five account routes and the routes that add, list and revoke passkeys); any other route is a **403** `account-recovery-required`, whatever its `auth` mode but `none`. A route is closed to it by default, so a new route cannot be open to it by accident. Setting a new password (`PUT /password`) or confirming an authenticator (`POST /totp/confirm`) makes the session `full`.
- **A passkey sign-in is two requests, with no address and no password.** `POST /login/passkey/options` makes a challenge that belongs to no one and answers `{ challenge, options }`; `POST /login/passkey/verify` takes the challenge and the browser's response and, in one transaction, calls `finishPasskeyLogin` and creates the session (method `passkey`), exactly as the other login steps do. Every failure is the same 401 `sign-in-failed`, whether the credential is unknown or revoked, the user disabled, the signature wrong or the counter back, and the cause is in the audit trail as a reason class.
- **Adding a passkey is two requests too, and a recovery session may make them.** `POST /passkeys/register/options` and `POST /passkeys/register/verify` need a session and the right `Origin`, count against the limit per session, and say `allowedInRecovery`: adding a passkey is how a user who came in with a recovery code sets a new way to sign in, and it makes that session `full`. Every refusal is the same 422 `passkey-registration-failed`; the user is signed in, so it is not a 401.
- **Listing and revoking are open to a recovery session; renaming is closed to it.** A person who came in with a recovery code or an admin reset link because a device was lost must be able to see which passkeys are theirs and remove the lost one, so `GET /passkeys` and `DELETE /passkeys/:id` say `allowedInRecovery` and `PATCH /passkeys/:id` does not. The id of another user's passkey, one that is not there and a revoked one give the same 404, because the core checks the owner in the statement that writes. A passkey sign-in makes its session with the passkey that opened it (`checked.passkeyId`), and revoking the passkey ends the sessions it opened, the one making the request included: its cookie is then no good, and the next request is a 401 that clears it. Revoking a user's last way to sign in (no password, no other live passkey) is a 409 `last-sign-in-method`: the route turns the core's `AuthStateError` of that reason into its own error class, and any other `AuthStateError` stays the error table's.
- **The relying party comes from `OSFPM_PUBLIC_URL`.** `buildApp` makes it once with the core's `relyingPartyFor` and registers the login and passkey plugins with it: the id is the host name and the origin is the only origin a ceremony may happen on. **Changing the host of the public URL makes every existing passkey unusable**; see `packages/api/README.md`.
- **The WebAuthn forms are listed field by field.** The response schemas in `passkey-schemas.ts` name every field of the library's JSON types and nothing else, so a response is an allow-list of what a client is told; the request schemas check the shape and the size of what the browser sends, and the library verifies it. A body that is not shaped right is a 400; one that is shaped right and does not verify is the refusal of its route.
- **The login routes are `auth: 'none'`** and set `authRateLimit`: at most 10 requests a minute per address, counted together across the five. They use no session, so cookies are ignored. The four that make a session (`password`, `totp`, `recovery` and `passkey/verify`) and the two setup routes say `requireOrigin`, so the plugin refuses a `POST` with no `Origin`, or with one that is not the public origin, with a 403 `origin-mismatch`, cookie or not: a page on another site could otherwise sign the visitor in as someone else. It comes right after the strict limit, so a refused request is counted and spends nothing, and before the body is read. `passkey/options` makes no session and takes any `Origin`. Each place a route makes a session calls `assertOriginRequired`, so a route that forgets the option answers a 500 in its first test. Every account route is `auth: 'required'` with `sessionRateLimit`, so it needs a session and, for a request that changes data, the right `Origin`.
- **A current password that is not accepted is a 403** `current-password-incorrect` on the account routes: the user is signed in, so it is not a 401. The answer is the same for a missing, a wrong and a throttled password. A wrong guess counts toward the same per-account throttle as a failed sign-in, so a stolen session cannot be used to guess the password.
- **What the user is shown once** (an authenticator secret and its `otpauth://` address, a challenge, a passkey challenge, recovery codes) comes in an uncacheable response (`Cache-Control: no-store`) and is never returned, logged or audited again. A session token goes only into the cookie.
- **A refused new password is a 422** `password-refused`. The reason is `errors[0].code` (`too-short`, `too-long`, `too-common`, `too-predictable`, `contains-email` or `contains-product-name`) and `detail` says what to do. The policy is in the core (`password-policy.ts`) and is never applied to a sign-in.

**Rules you must not break**

- A route declares `auth`. A route that makes a session sets `requireOrigin`. A route that checks a secret sets `authRateLimit`. A route that a user who came in with a recovery code needs sets `allowedInRecovery`, and nothing else does.
- Login failures always answer the same 401 `sign-in-failed`. Never add a cause to the body, the headers, the status or the timing of a failure.
- A secret (a password, code, challenge, token or authenticator secret) is never logged, never put in an error body and never put in an audit event. Log lines hold the known keys or plain scalars only.
- A handler does not catch the core's failures to answer them itself: it throws the API's own error classes (`src/errors.ts`) and the error table maps them.

**Tests:** `pnpm test packages/api/src/auth`. `login-routes.test.ts`, `account-routes.test.ts` and `passkey-routes.test.ts` run the routes through `app.inject()` (the last answers the browser's WebAuthn calls with the core's software authenticator, so the library's real verification runs); `recovery-scope.test.ts` tests the scope on routes that exist only in the test, and that a session opened by a recovery code, a reset link, setup or an invite gets the same 403 with the same detail; `secrets-in-flows.test.ts` runs every flow, the passkey ones included, and looks for every secret (a challenge, a credential id, a public key, a signature among them) in the logs (at every level), the audit and change events, the error bodies and every table. The rest cover the plugin and the limits. They run on PGlite, and on PostgreSQL too when `DATABASE_URL` is set. A test that sends many requests gives each its own `remoteAddress`, so the rate limits measure only what the test means them to.
