# auth

The building blocks of login (spec card SC-10, decision D-56): secret tokens and codes, Argon2id passwords and the password policy, sessions, recovery codes, authenticator-app codes (TOTP), the half-finished sign-in between a password and a code, the per-account throttle, and the one-time setup code, each with its audit events. There are no routes or cookies here: the API package has the session cookie, the auth plugin and the session routes (P-03b2), and the login and account routes (P-03b3a). Passkeys (WebAuthn), invites and the first-run flow are not built yet; they come in P-03b3b and P-03b4.

**Entry points**

- `tokens.ts`: `generateToken` (32 random bytes, base64url) and `hashToken` (SHA-256). `generateHumanCode`, `normaliseHumanCode` and `hashHumanCode` make and check the typeable codes (16 characters of Crockford base32, 80 bits) used for recovery and setup codes.
- `password.ts`: `hashPassword` and `verifyPassword` (`{ ok, needsRehash }`) with Argon2id as a PHC string. Parameters are in `PASSWORD_HASH_PARAMS`. It uses the built-in `crypto.argon2`, not a package: the Node docs for the version in `.nvmrc` mark the `node:crypto` module `Stability: 2 - Stable` and give `crypto.argon2` no lower stability of its own. They hash exactly the string they are given.
- `password-policy.ts`: `normalisePassword` (Unicode NFC), `checkPassword` (length 15 to 256 code points after normalisation, a blocklist, no composition rules) and `describePasswordRefusal`. The numbers are in `PASSWORD_POLICY`, marked `verified: false`. `password-blocklist.ts` is the list.
- `password-service.ts`: `verifyPasswordLogin` (the password step), `setPassword` and `checkCurrentPassword` (the re-check before a change).
- `totp.ts`: `enrolTotp`, `confirmTotp`, `removeTotp` and `verifyTotp`, over the `otpauth` package. The settings are in `TOTP_SETTINGS`.
- `login-challenge.ts`: `createLoginChallenge` and `consumeLoginChallenge`, the second step of a sign-in. The limits are in `LOGIN_CHALLENGE`.
- `throttle.ts`: `isThrottled`, `recordLoginFailure` and the limits in `LOGIN_THROTTLE`.
- `login-user.ts`: `normaliseEmail` and `findLoginUser`, which turn a typed address into an account.
- `sessions.ts`: `createSession`, `validateSession`, `revokeSession`, `revokeUserSessions`, `listUserSessions`, `promoteSession`, `disableUser`, `enableUser`. Lifetimes are in `SESSION_DEFAULTS` (12 hours idle, 30 days absolute).
- `recovery.ts`: `generateRecoveryCodes` (ten, replacing any earlier set), `consumeRecoveryCode` (single use) and `verifyRecoveryLogin` (the recovery step of a sign-in).
- `setup-code.ts`: `issueSetupCode` (24 hours, revokes the earlier live code), `consumeSetupCode` and `isSetupComplete`.
- `shared.ts` and `errors.ts`: the audit categories (`AUTH_AUDIT`), `AuthInputError` and `AuthStateError`, and helpers the services share. `test-support.ts` seeds an installation, users, passwords and authenticators for tests.

Pass the transaction handle to every function, and the time as `now`. The services check no permission: the route that calls them has decided who may.

**How a sign-in goes**

1. `verifyPasswordLogin` checks the address and password and answers `{ ok, user, totpRequired }`. With no confirmed authenticator the route makes a session (`createSession`, method `password`). With one, it makes a challenge (`createLoginChallenge`) and no session.
2. `consumeLoginChallenge` takes the challenge and the authenticator code. A right code makes the route create a session of method `password+totp`.
3. `verifyRecoveryLogin` takes the address and a recovery code, uses the code up, and ends every other live session of the user (reason `recovery-used`, one `auth.sessions-revoked` event), because the person lost a way to sign in and a session that is not theirs may be live. The route then makes a session of method `recovery`, which `createSession` always gives the scope `recovery`: it may only set a new way to sign in. `setPassword` or `confirmTotp`, called with that session, turn it into `full` (`promoteSession`). The API plugin enforces the scope; the services only record it.

Each step runs in one transaction, which the caller opens, so the user row lock the step takes is held until the session exists.

**How it works**

- A token or code is random and shown to the caller once. Only its SHA-256 hash is stored, and the row is found by that hash. SHA-256 is enough because the values hold at least 80 bits of randomness; passwords are low-entropy, so they use Argon2id instead. A login challenge is a 32-byte token, handled like a session token.
- A session lasts 12 hours without a request and 30 days in all. A request slides the idle end, never past the absolute end, and writes at most once a minute. A disabled or deleted user's session is not valid, and disabling a user revokes their sessions.
- A password is normalised with NFC in one place (`normalisePassword`) before the policy, before the hash and before a login check, so the set and the check cannot disagree. NFC makes a letter with a composed accent and the same letter with a combining accent one password; it leaves compatibility forms alone, so a full-width spelling is another password. The policy refuses 14 code points and accepts 15, accepts 256 and refuses 257, counting after normalisation (some characters, such as U+0958, are written as two code points by NFC). It then refuses a whole password that is on the blocklist (compared without regard to case, spelling form or the separators `space - _ .`: the comparison also folds compatibility forms with NFKC, so a full-width spelling of a listed password is refused, but what is hashed is never folded), a password that contains a word of the user's own address or `osfpm`, and a whole password that repeats a unit shorter than 15 code points or counts along a keyboard row or the alphabet. There is no composition rule. The reason is given to the person setting the password, never at login.
- The authenticator uses SHA-1, six digits and thirty seconds, which every app supports. A code is accepted from one step either side of now and never from a step at or before the last one used, which `verifyTotp` enforces in one conditional UPDATE, so two requests with one code succeed once. `confirmTotp` uses up the step of the first code. `enrolTotp` refuses once an authenticator is confirmed: replacing it would switch the second step off without a password, so it has to be removed first, which asks for one.
- A challenge lasts five minutes, allows five code attempts and works once. The user row, then the challenge row, are locked while an attempt is judged, so two requests with one challenge, even with two different right codes, sign in once.
- Setting a password revokes the user's other sessions, as does removing the authenticator (reason `totp-removed`). Using a recovery code revokes all of them (reason `recovery-used`), before the recovery session is made, so that session is not one of them; a failed attempt revokes nothing.
- Each security-relevant change writes one `audit_event`. The `auth.*` categories are `session-created`, `session-revoked`, `sessions-revoked`, `session-promoted`, `user-disabled`, `user-enabled`, `recovery-codes-generated`, `recovery-code-used`, `setup-code-issued`, `setup-code-used`, `login-step-passed`, `login-step-failed`, `password-set`, `totp-enrolled`, `totp-confirmed` and `totp-removed`. Details hold scalar values such as a method, a reason or a count, never a secret.
- Rows carry the server's own id as `origin_server`, read with `getServerId` (`src/installation/`) from the `installation` row, so the services refuse until that row exists. `serverId` in `shared.ts` wraps it for them, with `AuthStateError`.

**Failures, the audit trail and the throttle**

- A failed step is a returned value, not a thrown error: `{ ok: false }` with no reason. The reason is for the audit trail alone, so the caller gives one answer for every failure and a caller learns nothing about which it was. The services return rather than throw so the caller's transaction commits and the audit event survives (CLAUDE.md, Data rules).
- A failure is audited as `auth.login-step-failed` with the method (`password`, `totp` or `recovery`) and a reason class from `LOGIN_FAILURE_REASONS`: `unknown-account`, `wrong-secret`, `throttled`, `disabled` or `challenge-invalid`. It never holds a submitted value: no password, code, token or typed address, and no hash of one. Its actor is `system`. Its target is the user only when the server found them by its own means; for an address it does not know there is no target and the address is not written down. A check of the current password by someone already signed in is the same event with `purpose: 'reauthenticate'`.
- A refusal by the password policy, a wrong code at `confirmTotp` and a missing current password are not audited: no secret was guessed.
- **The throttle:** five `wrong-secret` events for one account in fifteen minutes close that account's password, authenticator, recovery and current-password checks until the oldest failure is fifteen minutes old. The count is of audit events (through the index on `audit_event` target and time), so there is no second counter. It counts every method together, so a guesser cannot spread guesses over them. A refused attempt writes `throttled`, which is not counted, so refused attempts do not keep an account closed: there is no permanent lock-out. A throttled account's secret is not checked at all, even if it is right, and a recovery code is not used up.
- **Equal time:** every `verifyPasswordLogin` attempt costs one Argon2 derivation. An unknown address, an account with no password, a disabled account and a throttled one hash a stand-in (`EQUAL_TIME_INPUT`) instead of checking a password, so the time taken does not say which it was. A test counts the derivations rather than timing them.

**Rules you must not break**

- Tables in `SECURITY_TABLES` are written only here, directly, never through the write helper. Their changes are audited, not change-logged. `src/db/write-helper-scan.test.ts` fails when another file writes them, or when a tenant table is written outside the write helper. `login_challenge` is one.
- A raw token, code, challenge or password is never stored, logged, audited or returned after it is first given out, and neither is a hash of one. The authenticator secret is stored only in `totp_credential.secret`, a column marked sensitive, because a code cannot be checked without it. `enrolTotp` returns it once, in the same response as its `otpauth://` address, and nothing returns it again. `listUserSessions` and `validateSession` return no hash.
- `user` and `installation` are written only by the services named in `SERVICE_WRITTEN_TABLES`, which is `auth` for both today, and never through the write helper. Here, `disableUser`, `enableUser` and `createSession` write `user`, and each is audited. The scan in `write-helper-scan.test.ts` enforces it.
- Every database failure becomes a `RecordWriteError` with the SQLSTATE and constraint name only (`guardedAuth`), because driver messages carry the query parameters, which here are hashes.
- A string from a caller is checked against a constant list (`SESSION_METHODS`, `SESSION_SCOPES`, `SESSION_REVOKE_REASONS`, `LOGIN_METHODS`, `LOGIN_FAILURE_REASONS`, the code alphabet) and never used as a key.
- Lock order: a service that checks a user's state and then writes takes the user row first (`lockUser`), then, where it uses one, the challenge row; the setup-code functions take the `installation` row. Nothing here touches a project, so the project change counter does not come into it.
- `isThrottled` and `checkCurrentPassword` are called with the user's row locked, so two guesses at once cannot both read four failures.
- The password policy is for setting a password. A login attempt never goes through it, and its reasons never reach a login answer.
- No setup code is issued, or accepted, once `installation.setup_completed_at` is set.

**Decided in P-03b3a, and limits to know**

- NFC is the normalisation, as NIST SP 800-63B-4 (section 3.1.1.2) says a verifier should apply before hashing. The comparison with the blocklist and with the user's address still folds compatibility forms (NFKC), because a looser comparison refuses more; it never changes what is hashed.
- A blocklist entry must match the whole password (SP 800-63B-4, section 3.1.1.2). A word of the user's address or `osfpm` may sit inside the password, because the reason given is "contains your email". Parts of an address shorter than four characters are ignored.
- The blocklist is a small list written for this project plus the pattern rules above. NIST says a very large list adds little when guessing is throttled. Its source and licence are in the header of `password-blocklist.ts`.
- The throttle means someone who knows an address can keep that account's password, authenticator and recovery sign-in closed by guessing; the passkey sign-in, when it exists, will not be affected.
- `verifyPassword` reports `needsRehash` but nothing acts on it yet, because every hash is made with the current parameters.
- The password step runs Argon2 while it holds the user row lock, inside a transaction, so a slow hash is paid under the lock. On PGlite, which has one connection, that holds the database for the length of one hash (tens of milliseconds); on PostgreSQL it waits only for other attempts on the same account.
- The equal-time guarantee is for the password step. The recovery step is a database lookup either way and does not hide whether an address has an account by time; every answer is still the same.
