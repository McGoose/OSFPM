# auth

The building blocks of login (spec card SC-10, decision D-56): secret tokens and codes, Argon2id passwords and the password policy, sessions, recovery codes, authenticator-app codes (TOTP), passkeys (WebAuthn), the half-finished sign-in between a password and a code, the per-account throttle, and the one-time setup code, each with its audit events. There are no routes or cookies here: the API package has the session cookie, the auth plugin and the session routes (P-03b2), the login and account routes (P-03b3a), and the passkey routes (P-03b3b). First-run setup, which makes the first organisation, its Administrator role and the first administrator, is here (`first-run-setup.ts`), with its HTTP side in the API package (`src/setup/`). Invites (`invites.ts`) and admin reset links (`access-reset.ts`) are here too, with their HTTP side in the API package.

**Entry points**

- `tokens.ts`: `generateToken` (32 random bytes, base64url) and `hashToken` (SHA-256). `generateHumanCode`, `normaliseHumanCode` and `hashHumanCode` make and check the typeable codes (16 characters of Crockford base32, 80 bits) used for recovery and setup codes.
- `password.ts`: `hashPassword` and `verifyPassword` (`{ ok, needsRehash }`) with Argon2id as a PHC string. Parameters are in `PASSWORD_HASH_PARAMS`. It uses the built-in `crypto.argon2`, not a package: the Node docs for the version in `.nvmrc` mark the `node:crypto` module `Stability: 2 - Stable` and give `crypto.argon2` no lower stability of its own. They hash exactly the string they are given.
- `password-policy.ts`: `normalisePassword` (Unicode NFC), `checkPassword` (length 15 to 256 code points after normalisation, a blocklist, no composition rules) and `describePasswordRefusal`. The numbers are in `PASSWORD_POLICY`, marked `verified: false`. `password-blocklist.ts` is the list.
- `password-service.ts`: `verifyPasswordLogin` (the password step), `setPassword` and `checkCurrentPassword` (the re-check before a change).
- `totp.ts`: `enrolTotp`, `confirmTotp`, `removeTotp` and `verifyTotp`, over the `otpauth` package. The settings are in `TOTP_SETTINGS`.
- `login-challenge.ts`: `createLoginChallenge` and `consumeLoginChallenge`, the second step of a sign-in (the `totp` kind only), `createPasskeyChallenge` and `usePasskeyChallenge`, the one-time challenges of a passkey step, and `cleanupExpiredChallenges(tx, now)`, which deletes every expired challenge and is for the future worker. The limits are in `LOGIN_CHALLENGE`.
- `throttle.ts`: `isThrottled`, `recordLoginFailure` and the limits in `LOGIN_THROTTLE`.
- `login-user.ts`: `normaliseEmail` and `findLoginUser`, which turn a typed address into an account.
- `sessions.ts`: `createSession`, `validateSession`, `revokeSession`, `revokeUserSessions`, `revokePasskeySessions`, `listUserSessions`, `promoteSession`, `disableUser`, `enableUser`, and `cleanupEndedSessions(tx, now)`, which deletes the sessions that ended a set time ago and is for the worker. Lifetimes, and how long an ended session is kept, are in `SESSION_DEFAULTS` (12 hours idle, 30 days absolute). A session of method `recovery` or `reset` always has the `recovery` scope.
- `recovery.ts`: `generateRecoveryCodes` (ten, replacing any earlier set), `consumeRecoveryCode` (single use) and `verifyRecoveryLogin` (the recovery step of a sign-in).
- `passkeys.ts`: `relyingPartyFor`, `startPasskeyRegistration`, `finishPasskeyRegistration`, `startPasskeyLogin`, `finishPasskeyLogin`, `listPasskeys`, `renamePasskey` and `revokePasskey`, over `@simplewebauthn/server`. The settings are in `PASSKEY_SETTINGS`.
- `setup-code.ts`: `issueSetupCode` (24 hours, revokes the earlier live code), `consumeSetupCode`, `checkSetupCode` (whether a code is live, without using it up), `isSetupComplete`, `lockInstallation` (the one lock setup serialises on) and `cleanupSetupCodes(tx, now)`, which deletes the codes that were used, revoked or expired and is for the worker.
- `invites.ts`: `createInvite` (needs `members:invite`, and gives nothing the person making it does not hold), `listInvites`, `revokeInvite`, `inspectInvite` (what the holder of a live token may be told) and `acceptInvite` (a signed-in user or a new account joins the organisation). The refusals are in `invite-errors.ts`, all extending `InviteRefusedError` except `InviteExceedsOwnAccessError`. Invite tokens are made and stored like session tokens: only the hash.
- `invite-cleanup.ts`: `cleanupInvites(tx, now)`, which deletes the invites that were used, revoked or expired, and their role links with them, and is for the worker. The `invite` and `invite_role` tables are in `src/db/schema/invite.ts`.
- `access-reset.ts`: `createAccessReset` (needs `members:reset-access` and the seven rules for who may reset whom, and revokes every earlier link of the person that was neither used nor revoked, expired ones too: one live link per person), `revokeAccessReset`, `inspectAccessReset` (when a live link ends, and nothing about the person) and `useAccessReset` (ends every session of the person, clears their password, authenticator and recovery codes, and the passkeys if the link says so). The refusals are in `access-reset-errors.ts`: `AccessResetInvalidError` is the one answer for a link that does not work, and the six rule errors extend `ResetNotAllowedError`. Reset tokens are made and stored like session tokens: only the hash.
- `access-reset-cleanup.ts`: `cleanupAccessResets(tx, now)`, which deletes the reset links that were used, revoked or expired and is for the worker. The `access_reset` table is in `src/db/schema/access-reset.ts`.
- `api-token-permissions.ts`: `API_PERMISSIONS`, the catalogue rows of `api:manage` (the two organisation switches for personal API tokens, and listing and revoking any token of the organisation) and `api:tokens` (making a token, and the permission a token needs its owner to hold each time it is used). Neither is sensitive, both are classed `write`, and the start-up top-up gives both to the Administrator role. The `api_token` table is in `src/db/schema/api-token.ts`, and the two switches (`api.personal-tokens` and `api.personal-tokens.sensitive`) are read by `readApiTokenSwitches` in `src/access/`.
- `api-tokens.ts`: `getApiTokenSwitches` and `setApiTokenSwitches` (read and change the two organisation switches, `api:manage`), `createApiToken` (`api:tokens`), `listOwnApiTokens` and `revokeOwnApiToken` (no permission: your own), `listOrganisationApiTokens` and `revokeAnyApiToken` (`api:manage`), `revokeApiToken` (the one entry for the route: any token for `api:manage`, otherwise the person's own), `authenticateApiToken` (a raw token to its credential and owner, or one `ApiTokenInvalidError`), `recordApiTokenCall` (the audit event of one outside call) and `revokeApiTokensOfUser` (what `useAccessReset` calls). The token is `osfpm_pat_` and 43 characters of base64url, shown once. See "How personal API tokens work" below.
- `api-token-errors.ts`: the refusals, all extending `ApiTokenRefusedError`: `ApiTokenInvalidError` (the one answer for a token that does not work, with the reason for the audit trail), `ApiTokensDisabledError`, `ApiSensitiveTokensDisabledError`, `NotASensitivePermissionError` (where in the list, never the keys) and `TokenExceedsOwnAccessError` (the keys, which are catalogue names).
- `api-token-cleanup.ts`: `cleanupApiTokens(tx, now)`, which deletes the personal API tokens that were revoked or have expired and is for the worker. A token that never expires is never deleted for being old.
- `escalation.ts`: `uncoveredPermissions`, `grantsOfRoles` and `grantsOfMember`, the rule against escalation that `createInvite` and `createAccessReset` share.
- `ensure-installation.ts`: `ensureInstallation`, which the server calls at start-up to make the single `installation` row, once, safe when servers start together, never replacing it.
- `users.ts`: `createUser`, the auth-owned writer of `user` (an active or invited account, the address normalised), and `isEmailShaped`.
- `administrator-role.ts`: `createAdministratorRole`, which makes the Administrator organisation role (a managed role, see `src/access/README.md`) and grants it every permission in `PERMISSION_LISTS`, `topUpAdministratorRoles`, which the server runs each time it starts to give every Administrator role the permissions added since, and `narrowManagedSensitiveGrants`, which it runs just before the permission sync to narrow a managed role's `all-projects` grants of a permission that is now sensitive.
- `first-run-setup.ts`: `completeFirstRunSetup(tx, input, now)`, which does first-run setup in one transaction, and the helpers `slugFromName`, `normaliseLocale` and `normaliseTimeZone`. The defaults for a locale and a time zone that were not given are in `SETUP_ORGANISATION_DEFAULTS`.
- `shared.ts` and `errors.ts`: the audit categories (`AUTH_AUDIT`), `AuthInputError` and `AuthStateError`, and helpers the services share, among them `lockUser`, which holds the user row `FOR NO KEY UPDATE`, or `FOR UPDATE` with `strength: 'update'`, or `FOR KEY SHARE` with `strength: 'key-share'` (the weakest, which only waits for a `FOR UPDATE` holder; the writers of API tokens take it). `test-support.ts` seeds an installation, users, passwords and authenticators for tests, and holds the software authenticator (see Passkeys).

Pass the transaction handle to every function, and the time as `now`. The services check no permission: the route that calls them has decided who may.

**How a sign-in goes**

1. `verifyPasswordLogin` checks the address and password and answers `{ ok, user, totpRequired }`. With no confirmed authenticator the route makes a session (`createSession`, method `password`). With one, it makes a challenge (`createLoginChallenge`) and no session.
2. `consumeLoginChallenge` takes the challenge and the authenticator code. A right code makes the route create a session of method `password+totp`.
3. `verifyRecoveryLogin` takes the address and a recovery code, uses the code up, and ends every other live session of the user (reason `recovery-used`, one `auth.sessions-revoked` event when it ended any), because the person lost a way to sign in and a session that is not theirs may be live. The route then makes a session of method `recovery`, which `createSession` always gives the scope `recovery`: it may only set a new way to sign in. `setPassword` or `confirmTotp`, called with that session, turn it into `full` (`promoteSession`). The API plugin enforces the scope; the services only record it.

4. `startPasskeyLogin` makes a challenge that belongs to no one, and `finishPasskeyLogin` takes it with the browser's response, finds the credential by its id, and answers `{ ok, user }`. The person gives no address and no password. The route then creates a session of method `passkey`.

Each step runs in one transaction, which the caller opens, so the user row lock the step takes is held until the session exists.

**How first-run setup goes** (SC-10, decision D-56, Q1)

1. At start-up the server makes the `installation` row (`ensureInstallation`) and, while `setup_completed_at` is NULL, issues a setup code and prints it to standard error (API package, `src/setup/`). The code is the only secret OSFPM prints.
2. The person gives the code, the organisation (name, country, base currency, and a locale and time zone if they want them) and the first administrator (address, display name and, if they want to, a password). `completeFirstRunSetup` does the rest, in one savepoint, so a refusal or a failure at any step undoes every step before it, the spent code included: lock the `installation` row and refuse if setup is already complete; spend the code; `createUser` (active, the address normalised) and, if a password was given, `setPassword` under the policy; the organisation, through the write helper, in its own sequence; the Administrator role and its grants; the owner membership (tier `owner`, active) linked to that role; `installation.setup_completed_at`.
3. It answers `{ ok: true, user, organisation, mustSecureAccount }`, or a refusal that is a returned value, not a thrown error: `code-invalid`, one answer for every way a code can be no good (unknown, expired, replaced, used, not shaped like a code, setup already complete), or `password-refused` with the policy's reason, which the person setting the password is owed. A bad code is audited as `auth.setup-check-failed` (purpose `setup`) after the savepoint is undone, so the event survives; a refused password is not audited, because no secret was guessed, and leaves the code unspent, so the person tries again with it.
4. The route makes the session in the same transaction: method `setup`, scope `full` with a password, `recovery` without one (`mustSecureAccount`), so the administrator must set a password or add a passkey before anything else, by the rule the session of a recovery code already follows.

- **The user is created before the organisation.** The write helper stamps `created_by` with its acting user, a foreign key to `user`, and the new user is the actor of every tenant write after it, so the user exists first. `user` is install-level and needs no organisation, so the order is open. The organisation is the first tenant row; the write helper takes its change counter after the row (see `src/db/README.md`).
- **The Administrator role** (key `administrator`, no project) holds every permission in `PERMISSION_LISTS`. A role holds one row for a permission without a department, so a permission that is not flagged `grants_sensitive` is granted `all-projects` (which also counts in the organisation) and a sensitive one `own-scope`, never `all-projects` (the database refuses it, and `hasProjectPermission` ignores one). The administrator therefore sees and edits every production's ordinary data without being a member of each, while sensitive crew data, contract amounts and cost amounts still need membership of the production (maintainer decision of 22 Nov, task P-03b4a; D-55). The role is **managed** (`role.managed`): an organisation cannot edit or delete it or its grants, and it is written only inside `withManagedRoleMaintenance`.
- **Topping the Administrator role up.** The server calls `topUpAdministratorRoles(tx, { now })` after the permission sync, each time it starts. It locks the `installation` row first, as setup does, so two servers that start together take turns and neither fails on the unique key of a grant. For every managed role with the key `administrator` and no project it adds each permission the role does not hold, with the reach setup gives it, through the write helper with the system as the writer (a change event each), and writes one `auth.administrator-role-topped-up` event for the organisation with the count and no permission key. It only adds: it takes nothing away and leaves a grant that exists as it is, whatever its reach. A call that adds nothing writes nothing, takes no change counter and makes no event. A permission that a release newly flags as sensitive while the role holds it for all projects is handled by `narrowManagedSensitiveGrants`, not by the top-up (see the next point).
- **Narrowing a managed grant when a permission turns sensitive.** The server calls `narrowManagedSensitiveGrants(tx, { now })` in the transaction of the permission sync, before any list is synced, because the database refuses to flag a permission sensitive while an `all-projects` grant of it exists, and the managed-role trigger refuses an operator who narrows the grant by hand. It locks the `installation` row first (the same first lock as the top-up; before that row exists no managed role does, so it does nothing), then, for every permission the lists flag sensitive, narrows each `all-projects` grant on a managed role to `own-scope` (a removed grant too, because the database counts it), through the write helper with the system as the writer and the managed-role triggers off (a change event each). It writes one `role.grant-reach-reduced` event for each grant, naming the role, the permission and both reaches. A role an organisation made is left alone: its grant still stops the sync with `PermissionSyncError`, which says the release must ship a migration that narrows it, and the narrowing is taken back with the sync, because they share a transaction. A call that narrows nothing writes nothing, so the second start-up does nothing.
- **Audit:** `auth.setup-code-used`, `auth.user-created` (from the system, no address), `auth.password-set` (when a password was given), `auth.organisation-created`, `auth.role-created`, `auth.membership-created` and `auth.setup-completed` (the organisation and user ids), the last four naming the organisation, and later `auth.administrator-role-topped-up` (the organisation and the role, with a count) and `role.grant-reach-reduced` (the one category not under `auth.`: the role, the permission and both reaches). Never a code, a password or an address.
- **Two setups at once with one code:** the first takes the `installation` row lock, the second waits for it and finds the code spent or setup complete, so one succeeds and the other gets `code-invalid`. The conditional update that spends the code would stop the second as well; what only the lock decides is a server that starts and issues a code while setup completes, which `issueSetupCode` then refuses (`setup-complete`) instead of leaving a live code.

**How invites work** (SC-10, decision D-57)

- **What they are.** An administrator makes a one-time link (`createInvite`), shows it once and passes it on; OSFPM sends nothing. The token is made and stored like a session token (`generateToken`, only the SHA-256 hash, found by that hash). `invite` and `invite_role` are security tables written only here, audited and not change-logged, and the write helper refuses them. `invite` carries `organisation_id` by declaration (`organisationScoped`), and `invite_role` is tied to its invite and to each role by composite keys on it, so an invite cannot attach another organisation's role. `invite_role` has no retention class: its rows go with their invite, and `cleanupInvites` removes both.
- **The link** is `<OSFPM_PUBLIC_URL>/invite#<token>`, built by the API. The token is in the fragment, which a browser never sends to a server, a proxy or in a `Referer` header (see the API README, "Invite links").
- **No escalation.** `createInvite` needs `members:invite` and refuses (`InviteExceedsOwnAccessError`, listing the keys) an invite whose roles hold a permission the person making it lacks in the organisation, or an `all-projects` grant they hold only for the organisation (`organisationPermissionReaches` in `src/access/`). A tier gives no exception: it grants nothing (D-51). Every role must be a live organisation role of the organisation, or it is an `AuthInputError` `roleIds`.
- **Inspecting and accepting** take the token as the capability and check no permission. `inspectInvite` answers the organisation's name, the end and whether an address is needed. Every bad token is one `InviteInvalidError` (unknown, expired, revoked or used); the cause goes into the audit event, which is written before the error is thrown (the caller commits). `acceptInvite` takes a signed-in user (who must be active) or a new account `{ email, displayName, password? }`, and in one savepoint marks the invite used, makes the membership (active, the invite's tier) and links its roles, as first-run setup does. A role deleted since the invite was made is left off. Refusals leave the invite usable and are audited with a reason code after the savepoint is undone: `InviteEmailMismatchError`, `AlreadyMemberError` (any existing membership row, a removed one too), `AccountExistsError` (also when two accepts create the same address at once) and, not audited because no secret was guessed, `InvitePasswordRefusedError`.
- **Locks.** An accept reads the invite, takes the organisation's change counter (`lockOrganisationChanges`), locks the invite row `FOR UPDATE` and judges it again, then locks the user row `FOR UPDATE` (always last: `lockUser` with `strength: 'update'`, which also holds off any insert that points at the user), and only then does the write helper make the membership. Two accepts of one token queue on the counter and the second finds the invite used; an accept and a revoke meet on the row. A revoke and a create take no counter, only the row, and no writer that holds an organisation's counter ever waits for an invite row, so they cannot form a cycle with an accept.
- **Audit:** `auth.invite-created` (the invite, the organisation, the tier, the role ids as one string, the expiry, and whether an address is set), `auth.invite-inspect-failed`, `auth.invite-accept-refused` (a reason code), `auth.invite-accepted` (the invite, the user, whether the account is new) and `auth.invite-revoked`. Never a token, a hash, an address or a password.
- **Members.** `listMembers` is in `src/members/`: it needs `members:read` and shows no sign-in detail.

**How admin reset links work** (SC-10, decision D-57, which closes O-14)

- **What they are.** An administrator makes a one-time link (`createAccessReset`) for a member who is locked out, shows it once and passes it on; OSFPM sends nothing. The token is made and stored like a session token (`generateToken`, only the SHA-256 hash, found by that hash). `access_reset` is a security table written only here, audited and not change-logged, and the write helper refuses it. It carries `organisation_id` by declaration (`organisationScoped`), and a composite key to `org_membership` on (`organisation_id`, `user_id`) makes the person a member of the organisation that issued it. The link is `<OSFPM_PUBLIC_URL>/reset#<token>`, built by the API, with the token in the fragment as for invites.
- **Who may reset whom**, in `checkRules`, checked when the link is made and again when it is used with the person who made it as the actor: (1) the actor holds `members:reset-access` in the organisation and can still sign in; (2) the person is not the actor (`CannotResetSelfError`: people reset themselves with their recovery codes); (3) every membership the person has, in any status and deleted rows too, is in this organisation (`UserInOtherOrganisationsError`: an administrator of one company must not take over an account that also belongs to another; such a person recovers with their own recovery codes or through the server's own administration); (4) an owner can only be reset by an owner (`OwnerResetNeedsOwnerError`); (5) no escalation: the actor holds every permission the person holds in the organisation, at the same reach or wider, by the rule invites use (`escalation.ts`; `ResetExceedsOwnAccessError` lists the keys, and a tier is no exception, D-51); (6) the person's account is active (`UserNotActiveError`). A creator without the permission and a person who is not a member are the same `AccessDeniedError` with no scope, so an id cannot be probed. Making a link revokes any earlier live link for the same person, audited with the reason `superseded`.
- **What a use clears.** `useAccessReset`, in one savepoint, locks the link row (`FOR UPDATE`), then the person's user row (`FOR UPDATE`, last), checks the rules again, then revokes every live session of the person (reason `access-reset`) and every live personal API token of theirs (reason `access-reset`, counted in the event as `tokensRevoked`), deletes their password, deletes their authenticator secret and every recovery code, revokes their passkeys when the link says `removePasskeys` (revoked, not deleted, as `revokePasskey` does it: a session keeps a key to the passkey that opened it, and the credential id stays taken), and marks the link used. Passkeys are kept otherwise, so the person may still sign in with one. The person's account, address and memberships are not touched. The caller then makes the session, method `reset`, which `createSession` always gives the `recovery` scope: the person may only set a new password or add a passkey, as after a recovery code.
- **Inspecting and using** take the token as the capability and check no permission. `inspectAccessReset` answers when the link ends and nothing else, no name or address, and also refuses a link a use would refuse. Every bad token, and every link a rule now refuses, is one `AccessResetInvalidError`; the reason goes into the audit event (`auth.access-reset-inspect-failed`, or `auth.access-reset-use-refused` for a use), which is written before the error is thrown, so the caller commits and the event survives.
- **Locks.** None of making, revoking and using a link takes a change counter, and no writer that holds a counter ever waits for a link row. A revoke takes only the link rows. A use takes the link row first and the person's user row last (CLAUDE.md, Data rules), and nothing between; after it, the person's sessions and their personal API token rows (in id order). The writers of tokens take the acting person's user row `FOR KEY SHARE` before any token row, in that same order, so they cannot deadlock with a use (see "How personal API tokens work"). An accept of an invite for the same person takes the user row the same way, last and `FOR UPDATE`: whichever gets it first, the other waits, and the use then reads the person's memberships under the lock, so it finishes before a second membership exists or sees it and is refused. `FOR UPDATE` also holds off any other insert that points at the user (a foreign key check takes a key-share lock), so that does not rest on one writer. Two uses of one token use it once, and a use and a revoke end with the link used or revoked, never both, by the link row lock. Making a link takes the person's user row `FOR UPDATE` too (the rules depend on rows that point at the person, and two links for one person queue on it, both made, the later one live), judges the rules again under it, and supersedes the person's earlier links with `FOR UPDATE SKIP LOCKED`: it never waits for a link row while it holds the person's row, because a use holds its link row and waits for the person's row, which would be a deadlock. A link it skips is one a use or a revoke holds at that moment; if that one has not changed it yet, the unique index `access_reset_live_unique` refuses the new link and the caller gets a `ResetLinkBusyError` (a `RecordStateError`, a 409 `reset-link-busy` in the API), with nothing written; there is no retry.
- **Audit:** `auth.access-reset-created` (the link, the organisation, the person, the expiry, `removePasskeys`), `auth.access-reset-revoked` (reason `manual` or `superseded`), `auth.access-reset-inspect-failed` and `auth.access-reset-use-refused` (a reason code), and `auth.access-reset-used` (the person, the number of sessions revoked, whether a password was cleared and an authenticator removed, the numbers of recovery codes and passkeys removed). The sessions it ends also have the one `auth.sessions-revoked` event they always have. Never a token, a hash, a password or an address.
- **Cleanup.** `cleanupAccessResets(tx, now)` (`access-reset-cleanup.ts`, in `TRANSIENT_CLEANUPS`) deletes the links that were used, revoked or have expired, with the cut-off invites use.

**How personal API tokens work** (SC-10, decisions D-17 and D-68)

- **What they are.** A person makes a secret for their own scripts and tools (`createApiToken`, `api:tokens`), is shown it once and keeps it. OSFPM stores only the SHA-256 hash of its 43 random characters, made as a session token's is (the fixed `osfpm_pat_` start is public and is not hashed), and the first 8 characters after `osfpm_pat_` (the `prefix`), so tokens can be told apart. The token is `osfpm_pat_` and 43 characters of base64url (32 random bytes); the fixed start lets secret scanners, such as GitHub's, recognise a leaked one. `api_token` is a security table written only here, audited and not change-logged, and the write helper refuses it. It carries `organisation_id` by declaration (`organisationScoped`): composite keys to `org_membership` and `project` make the owner a member of the organisation and the project one of its projects.
- **A token acts as its owner, narrowed, and never beyond.** It is for one organisation, optionally one project, `read` or `write`, and may carry an explicit sensitive scope. What it may do is its owner's access at the moment of each request, narrowed by what the token says, so it can only ever hold less. The narrowing of the permission checks is in `src/access/`.
- **Two switches, both off by default** (the organisation settings `api.personal-tokens` and `api.personal-tokens.sensitive`, read by `readApiTokenSwitches` and written by `setApiTokenSwitches`, which needs `api:manage`). The sensitive switch only counts while tokens are on. Turning one **off** takes effect at once, in the same transaction: tokens off revokes every live token of the organisation (reason `switch-off`) and turns the sensitive switch off too; sensitive off revokes every live token that has a sensitive scope. Turning one on restores nothing. Each switch that changes is written through the write helper (a change event) and audited once, with the number of tokens it revoked. `createApiToken` and `authenticateApiToken` read the switches as well, so a token is refused even if a revocation was missed.
- **Making one.** `createApiToken` needs `api:tokens` and the tokens switch on. The name is 1 to 100 characters, trimmed, with no control character. The token lasts `expiresInDays` (1 to 3650) or, when the request says nothing, 365 days; `noExpiry: true` makes one that never expires and cannot be combined with `expiresInDays` (maintainer decision, D-68). Setting an expiry is advised: a token that never expires is a standing key that works until someone revokes it, so the listings (`neverExpires`) and the audit event of its creation say so. A `projectId` must be a live project of the organisation that the owner can reach (a membership of it, or a grant for every project); anything else is one `ProjectNotAvailableError`, whether the project does not exist, was deleted, is another organisation's or cannot be reached, so it says nothing about projects that are not the owner's (a value that is not an id is an `AuthInputError`). The sensitive scope, `sensitivePermissions`, needs the sensitive switch on; every key must be a permission flagged `grants_sensitive`; a `read` token may list only `read` permissions (`permissionAccess`), and a key that changes data is a `TokenReadOnlyScopeError` that gives its place in the list; and the owner must hold each key where the token works: in the organisation, by the rule against escalation of `escalation.ts`, for a token of the whole organisation, and through a membership of the project that holds it for a project token (a sensitive permission is never held for all projects).
- **Using one.** `authenticateApiToken` finds the token by its hash. It works only if it is not revoked and not past its end, the tokens switch is on (and the sensitive switch too, for a token with a scope), its owner's account is `active` and not deleted, the owner's membership of the organisation is `active` and not deleted, the owner still holds `api:tokens` in the organisation (`permission-missing`: the token is refused and not revoked, and works again when they hold the permission again), and the request does not name another organisation in its path than the token's (`wrong-organisation`). Anything else is one `ApiTokenInvalidError`, whatever the cause: the reason is in the audit event `auth.api-token-auth-failed`, which is written before the error is thrown and holds the token's id when it exists and never any part of what was sent. A caller that passes `auditFailure: false` gets the same error and no event; the API does that for an address that is already over the strict limit, so a flood of bad tokens writes no more rows than the limit allows. A value that is not shaped like a token is refused without a lookup. A token that works has `last_used_at` written at most once a minute, like a session. Member removal does not exist yet (P-04b): until it does, a membership that stops being `active` makes its tokens fail, and P-04b will revoke them as well, with `membership-ended`.
- **Listing and revoking.** `listOwnApiTokens` shows a person's live tokens and `listOrganisationApiTokens` the organisation's, with the owner's name (`api:manage`): metadata only, which is the prefix, access, scope, expiry and whether it never expires, and never a hash. Revoking is one conditional UPDATE, so two revokes of one token end with one revocation and a not found for the other. Listing and revoking your own needs no permission, because it only shows a person what is theirs and takes access away: a person who lost `api:tokens` still sees and ends the tokens they made, and a list with nothing of theirs is empty. A token that is not live, not there or not the person's is the same not found for everyone, so nobody can tell whose a token is. Taking `api:tokens` from a person does not revoke their tokens, but they stop working at once (`permission-missing`) and work again when the permission is back. Someone with `api:manage` ends them, or the switch does.
- **Locks.** The order is the counter, then the user row, then the token rows (CLAUDE.md, Data rules). `createApiToken` and `setApiTokenSwitches` take the organisation's change counter before they read or write a switch, so a token being made and a switch being turned off queue: either the token is made and then revoked, or it is refused. They, and every revoke, then take the acting person's user row `FOR KEY SHARE` (`lockUser`) before any token row. That is the order of `useAccessReset`, which holds a person's user row `FOR UPDATE` and then their token rows, so a person who revokes their own token while their own reset link is used, or an administrator whose own link is used while they turn a switch off, cannot deadlock with it: whoever comes second waits for the row, holding no token. A bulk revocation (a switch turned off, an admin reset link used) also locks the token rows in id order before it changes them, so two of them cannot deadlock either. **A token is not made by a session that a reset link has ended.** `createApiToken` is told the session it is made from (`sessionId`) and reads it again once it holds the person's row, which a reset used for the same person holds `FOR UPDATE`: a make that comes first is revoked by the reset (reason `access-reset`, counted in its event), and one that comes after finds the session revoked and makes nothing (`AuthStateError` `session-ended`, a 401). The key-share lock conflicts only with `FOR UPDATE`, so it excludes the use of a reset link, the accept of an invite that gives the person a membership, and every service that ends the person's sessions in bulk: a password change, removing the authenticator app, a recovery-code sign-in, disabling the person and revoking a passkey (for the sessions it opened). They all take the row `FOR UPDATE` before they revoke, so a token is never made from a session one of them has ended: a make that comes first is made while its session is live and stands (only a reset link also revokes tokens), and one that comes after finds the session ended. A sign-in makes sessions and ends none, so it takes the row at the default strength. `session-revocation-locks.test.ts` pins this on PostgreSQL.
- **Audit.** `auth.api-token-created` (the token, the owner, the project, the access, the sensitive keys, the expiry or `never`, the prefix), `auth.api-token-revoked` (the reason, and the owner), `auth.api-token-switch-changed` (which switch, on or off, and how many tokens it revoked), `auth.api-token-auth-failed` (a reason code) and `api.call` (one outside call: the token, its owner, the organisation, the method, the route pattern and the status, written by `recordApiTokenCall` after the response). Never a token, a hash, a name, a query string or a body.
- **Cleanup.** `cleanupApiTokens`, in `TRANSIENT_CLEANUPS`, deletes the tokens that were revoked or have expired.

**Passkeys (WebAuthn)**

- **The library does the WebAuthn.** `@simplewebauthn/server` parses and verifies every response: the origin, the relying party, the challenge, the signature, user presence and user verification, the CBOR and COSE formats. Nothing here parses or verifies WebAuthn by hand. What is here is the policy: which options to ask for, what to store, and when to refuse. Only attestation `none` is accepted.
- **The relying party** is the site a passkey belongs to (`relyingPartyFor`, from `OSFPM_PUBLIC_URL`): the id is the host name, the origin is the origin, and the name is `OSFPM`. A browser ties each passkey to the id. **Changing the host of the public URL makes every existing passkey unusable**: a passkey made for `films.example.org` does nothing on `osfpm.example.org`, so the people who used them have to sign in another way (a password or a recovery code) and add their passkeys again. Changing only the scheme or the port keeps them. An IP address cannot be an id: use a host name, and `localhost` for development.
- **Adding a passkey** (`startPasskeyRegistration`, `finishPasskeyRegistration`) asks for a discoverable credential (`residentKey: 'required'`, so a later sign-in needs no address), for the device to verify the person with a PIN, fingerprint or face (`userVerification: 'required'`), for no attestation, and for ES256 or RS256 keys. It excludes the user's live passkeys, so one device is not added twice; a revoked one is not excluded. The user handle the device keeps is the 16 bytes of the user's id. A credential id that is already registered, by anyone, is refused. A `recovery` session becomes `full` once a passkey is added (trigger `passkey-registered`); other sessions stay, because a passkey adds a way in and does not remove one.
- **Signing in** has no `allowCredentials`: the device offers the passkeys it has for this site, and the options say nothing about which credential ids exist. The account is found from the credential id, which maps only to its owner. If the response carries a `userHandle` it must be the owner's (the 16 bytes of the user's id), or the sign-in is refused as `verification-failed` (WebAuthn, section 7.2); a response with none is accepted, because a device may leave it out. The challenge is judged first, then whether the credential is known (a deleted user's is not), then whether it is revoked, then whether the user is disabled, then the response (`verification-failed`), then the counter.
- **The challenge** is a `login_challenge` row of kind `webauthn-register` (tied to the user) or `webauthn-login` (`user_id` NULL, so no one, until the credential is found; the CHECK `login_challenge_user_check` allows NULL only for it). The token is 32 random bytes in base64url and is also the WebAuthn challenge: `options.challenge` is the same string the client sends back, and only its SHA-256 hash is stored. It lasts five minutes and works once. **The first response that reaches it uses it up, right or wrong**, and the refusal is returned, not thrown, so the use is kept; a challenge of another kind or another user is not touched. The expired sign-in challenges that belong to no one are deleted by `cleanupExpiredChallenges` (the worker), not by `startPasskeyLogin`.
- **The signature counter.** When either the stored count or the new one is above 0, the new one must be higher, or the credential may have been cloned: the sign-in is refused (reason `counter-regressed`), the stored count is kept, and the passkey is not revoked. A device that always reports 0, as many synced passkeys do, is accepted. This is the WebAuthn rule (section 7.2), written here and not left to the library, whose own check is switched off by giving it a count of 0, so the refusal has its own audit reason. A count that goes back to 0 after counting is refused too.
- **Every user keeps a way to sign in.** `revokePasskey` refuses (`AuthStateError`, reason `last-sign-in-method`) to revoke the last live passkey of a user who has no password. A password, or another live passkey, allows it. Recovery codes do not count: they open a limited session, they are not a way to sign in. The user row is locked, so two revocations at once of the last two cannot both pass. A revoked passkey is kept with `revoked_at`, so its credential id stays taken and the trail can name it. **Revoking a passkey also ends the sessions it opened**, and no others: a session of method `passkey` records the passkey in `session.passkey_credential_id` (NULL for every other method, by `session_passkey_credential_check`), and `revokePasskey` calls `revokePasskeySessions`, which revokes the live ones with the reason `passkey-revoked` and writes one `auth.sessions-revoked` event with the count and the passkey's row id. A passkey that is revoked may have been lost or copied, so what it opened must not outlive it. The user's other sessions, whatever their method, stay, and so do the sessions of the user's other passkeys. If the session making the request was opened by that passkey, it ends too. The sign-in returns the passkey (`passkeyId`), and `createSession` takes it only for method `passkey` and only if it is a live passkey of that user.
- **Failures** are audited as `auth.login-step-failed` with the method `passkey` and one reason: `unknown-credential`, `revoked`, `disabled`, `verification-failed`, `counter-regressed` or `challenge-invalid`. A passkey is not a secret anyone guesses, so none of them counts toward the throttle, and a throttled account can still sign in with a passkey. The library's own error messages quote the challenge, so they are caught and dropped; no credential id, public key, signature or challenge is written to a log, an audit event or an error.
- **The software authenticator** (`softwareAuthenticator` in `test-support.ts`) is the authenticator and the browser of a ceremony in one object, for tests. It builds what a real one sends from Node's `crypto` (ES256, RS256 or EdDSA keys, the client data JSON, the authenticator data, a CBOR attestation object with `fmt: 'none'` made with the library's own CBOR helper, and the signature), so the tests run the library's real verification and not a stub. Its tweaks (another origin, another relying party, no user verification, a wrong signature, a given counter) each break one thing. `software-authenticator.test.ts` shows, with the library alone, that its responses are valid and that each tweak breaks exactly what it says.

**How it works**

- A token or code is random and shown to the caller once. Only its SHA-256 hash is stored, and the row is found by that hash. SHA-256 is enough because the values hold at least 80 bits of randomness; passwords are low-entropy, so they use Argon2id instead. A login challenge is a 32-byte token, handled like a session token.
- A session lasts 12 hours without a request and 30 days in all. A request slides the idle end, never past the absolute end, and writes at most once a minute. A disabled or deleted user's session is not valid, and disabling a user revokes their sessions.
- A password is normalised with NFC in one place (`normalisePassword`) before the policy, before the hash and before a login check, so the set and the check cannot disagree. NFC makes a letter with a composed accent and the same letter with a combining accent one password; it leaves compatibility forms alone, so a full-width spelling is another password. The policy refuses 14 code points and accepts 15, accepts 256 and refuses 257, counting after normalisation (some characters, such as U+0958, are written as two code points by NFC). It then refuses a whole password that is on the blocklist (compared without regard to case, spelling form or the separators `space - _ .`: the comparison also folds compatibility forms with NFKC, so a full-width spelling of a listed password is refused, but what is hashed is never folded), a password that contains a word of the user's own address or `osfpm`, and a whole password that repeats a unit shorter than 15 code points or counts along a keyboard row or the alphabet. There is no composition rule. The reason is given to the person setting the password, never at login.
- The authenticator uses SHA-1, six digits and thirty seconds, which every app supports. A code is accepted from one step either side of now and never from a step at or before the last one used, which `verifyTotp` enforces in one conditional UPDATE, so two requests with one code succeed once. `confirmTotp` uses up the step of the first code. `enrolTotp` refuses once an authenticator is confirmed: replacing it would switch the second step off without a password, so it has to be removed first, which asks for one.
- A challenge lasts five minutes, allows five code attempts and works once. The user row, then the challenge row, are locked while an attempt is judged, so two requests with one challenge, even with two different right codes, sign in once. An expired challenge is of no use and is deleted: `createLoginChallenge` deletes the expired ones of the user it makes a new challenge for (a challenge that ends at `now` is expired, and a refused call deletes nothing), and `cleanupExpiredChallenges` deletes all of them, whoever they belong to, for the rows of a user who never signs in again. Both are housekeeping and write no audit event. A challenge that is used but still has time left stays until it expires.
- The rows these services write that are of no use after a while (`session`, `login_challenge`, `setup_code`, `invite`, `access_reset`, `api_token`) are in the `transient` retention class, and each has a cleanup for the worker: `cleanupEndedSessions`, `cleanupExpiredChallenges`, `cleanupSetupCodes`, `cleanupInvites`, `cleanupAccessResets` and `cleanupApiTokens`, listed in `TRANSIENT_CLEANUPS` (`src/retention/`). A cleanup is housekeeping, so it writes no audit event and checks no permission. It changes no answer, because it deletes only rows the services refuse already. Deleting a used setup code does not reopen setup, which `installation.setup_completed_at` decides.
- A right password whose stored hash was made with other Argon2 parameters than the current ones (`verifyPassword` says `needsRehash`) is stored again with the current ones at that sign-in, under the user row lock, so two sign-ins at once rehash once. It is not a change of password: `changed_at` and `must_change` stay, and the audit event (`auth.password-rehashed`, from the system, no hash) says so. It costs that one sign-in a second Argon2 derivation, which only the person with the right password can see. Raise `PASSWORD_HASH_PARAMS` and every user's hash follows at their next sign-in.
- Setting a password revokes the user's other sessions, as does removing the authenticator (reason `totp-removed`). Revoking a passkey revokes only the sessions that passkey opened (reason `passkey-revoked`). Using a recovery code revokes all of them (reason `recovery-used`), before the recovery session is made, so that session is not one of them; a failed attempt revokes nothing. Using an admin reset link revokes all of them too (reason `access-reset`), for the same reason, and every live personal API token of the person with them.
- Each security-relevant change writes one `audit_event`. The `auth.*` categories are `session-created`, `session-revoked`, `sessions-revoked`, `session-promoted`, `user-disabled`, `user-enabled`, `recovery-codes-generated`, `recovery-code-used`, `setup-code-issued`, `setup-code-used`, `login-step-passed`, `login-step-failed`, `password-set`, `password-rehashed`, `totp-enrolled`, `totp-confirmed`, `totp-removed`, `passkey-registration-started`, `passkey-registered`, `passkey-renamed`, `passkey-revoked`, `installation-created`, `setup-check-failed`, `setup-completed`, `user-created`, `organisation-created`, `role-created`, `membership-created`, `administrator-role-topped-up`, `invite-created`, `invite-inspect-failed`, `invite-accepted`, `invite-accept-refused`, `invite-revoked`, `access-reset-created`, `access-reset-revoked`, `access-reset-inspect-failed`, `access-reset-used`, `access-reset-use-refused`, `api-token-created`, `api-token-revoked`, `api-token-switch-changed` and `api-token-auth-failed`, and two that are not under `auth.`, `role.grant-reach-reduced` and `api.call` (one outside call made with a token). Details hold scalar values such as a method, a reason or a count, never a secret.
- Rows carry the server's own id as `origin_server`, read with `getServerId` (`src/installation/`) from the `installation` row, so the services refuse until that row exists. The server makes the row when it first starts (`ensureInstallation`). `serverId` in `shared.ts` wraps it for them, with `AuthStateError`.

**Failures, the audit trail and the throttle**

- A failed step is a returned value, not a thrown error: `{ ok: false }` with no reason. The reason is for the audit trail alone, so the caller gives one answer for every failure and a caller learns nothing about which it was. The services return rather than throw so the caller's transaction commits and the audit event survives (CLAUDE.md, Data rules).
- A failure is audited as `auth.login-step-failed` with the method (`password`, `totp`, `recovery` or `passkey`) and a reason class from `LOGIN_FAILURE_REASONS`: `unknown-account`, `wrong-secret`, `throttled`, `disabled` or `challenge-invalid`, and, for a passkey, `unknown-credential`, `revoked`, `verification-failed` or `counter-regressed`. It never holds a submitted value: no password, code, token or typed address, and no hash of one. Its actor is `system`. Its target is the user only when the server found them by its own means; for an address it does not know there is no target and the address is not written down. A check of the current password by someone already signed in is the same event with `purpose: 'reauthenticate'`.
- A refusal by the password policy, a wrong code at `confirmTotp` and a missing current password are not audited: no secret was guessed.
- **The throttle:** five `wrong-secret` events for one account in fifteen minutes close that account's password, authenticator, recovery and current-password checks until the oldest failure is fifteen minutes old. The count is of audit events (through the index on `audit_event` target and time), so there is no second counter. It counts every method together, so a guesser cannot spread guesses over them. A refused attempt writes `throttled`, which is not counted, so refused attempts do not keep an account closed: there is no permanent lock-out. A throttled account's secret is not checked at all, even if it is right, and a recovery code is not used up.
- **Equal time:** every `verifyPasswordLogin` attempt costs one Argon2 derivation. An unknown address, an account with no password, a disabled account and a throttled one hash a stand-in (`EQUAL_TIME_INPUT`) instead of checking a password, so the time taken does not say which it was. A test counts the derivations rather than timing them.

**Rules you must not break**

- Tables in `SECURITY_TABLES` are written only here, directly, never through the write helper. Their changes are audited, not change-logged. `src/db/write-helper-scan.test.ts` fails when another file writes them, or when a tenant table is written outside the write helper. `login_challenge` is one.
- A raw token, code, challenge or password is never stored, logged, audited or returned after it is first given out, and neither is a hash of one. The authenticator secret is stored only in `totp_credential.secret`, a column marked sensitive, because a code cannot be checked without it. `enrolTotp` returns it once, in the same response as its `otpauth://` address, and nothing returns it again. `listUserSessions` and `validateSession` return no hash.
- `user` and `installation` are written only by the services named in `SERVICE_WRITTEN_TABLES`, which is `auth` for both today, and never through the write helper. Here, `createUser`, `disableUser`, `enableUser` and `createSession` write `user`, and `ensureInstallation` and `completeFirstRunSetup` write `installation`; each is audited. The scan in `write-helper-scan.test.ts` enforces it.
- Every database failure becomes a `RecordWriteError` with the SQLSTATE and constraint name only (`guardedAuth`), because driver messages carry the query parameters, which here are hashes.
- A string from a caller is checked against a constant list (`SESSION_METHODS`, `SESSION_SCOPES`, `SESSION_REVOKE_REASONS`, `LOGIN_METHODS`, `LOGIN_FAILURE_REASONS`, the code alphabet) and never used as a key.
- Lock order: a service that checks a user's state and then writes takes the user row first (`lockUser`), then, where it uses one, the challenge row; where it also holds a change counter or an invite or reset row, as an accept of an invite and a use of a reset link do, the user row comes last, `FOR UPDATE` (CLAUDE.md, Data rules); the setup-code functions take the `installation` row. A passkey sign-in reads the credential without a lock to learn whose user row to take, takes it, then uses up the challenge (one conditional UPDATE) and reads the credential again under the lock. Nothing here touches a project, so the project change counter does not come into it. First-run setup takes the `installation` row first (`lockInstallation`), then the setup code row, then the user row, and only then the organisation, whose change counter the write helper takes after the row. No other writer can reach an organisation that is not committed, so none can wait on that counter.
- `isThrottled` and `checkCurrentPassword` are called with the user's row locked, so two guesses at once cannot both read four failures.
- The password policy is for setting a password. A login attempt never goes through it, and its reasons never reach a login answer.
- No setup code is issued, or accepted, once `installation.setup_completed_at` is set.
- The setup code is the only secret OSFPM prints. It goes to standard error, written by hand at start-up, and never through the logger, an error, an audit event or a response. No setup code, password or address is ever in an audit event.

**Decided in P-03b3a, and limits to know**

- NFC is the normalisation, as NIST SP 800-63B-4 (section 3.1.1.2) says a verifier should apply before hashing. The comparison with the blocklist and with the user's address still folds compatibility forms (NFKC), because a looser comparison refuses more; it never changes what is hashed.
- A blocklist entry must match the whole password (SP 800-63B-4, section 3.1.1.2). A word of the user's address or `osfpm` may sit inside the password, because the reason given is "contains your email". Parts of an address shorter than four characters are ignored.
- The blocklist is a small list written for this project plus the pattern rules above. NIST says a very large list adds little when guessing is throttled. Its source and licence are in the header of `password-blocklist.ts`.
- The authenticator secret is stored as base32 in its marked-sensitive column, not encrypted. Encrypting it comes with server-key handling, before the security check.
- The throttle means someone who knows an address can keep that account's password, authenticator and recovery sign-in closed by guessing; the passkey sign-in is not affected, because a failed passkey sign-in never counts.
- The password step runs Argon2 while it holds the user row lock, inside a transaction, so a slow hash is paid under the lock. On PGlite, which has one connection, that holds the database for the length of one hash (tens of milliseconds); on PostgreSQL it waits only for other attempts on the same account.
- The equal-time guarantee is for the password step. The recovery step is a database lookup either way and does not hide whether an address has an account by time; every answer is still the same.
