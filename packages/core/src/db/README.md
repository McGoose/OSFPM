# db

The database layer: clients, the Drizzle schema, the write helper and the column conventions every table follows.

**Entry points**

- `createDatabase` and `migrate`: PostgreSQL or PGlite, one migration set (`client.ts`, `migrate.ts`). On PostgreSQL `migrate` holds an advisory lock for its whole run (`MIGRATION_LOCK_KEY`), so servers that start together take turns, and runs the migration on that same connection, so a pool of one is enough; PGlite takes no lock.
- `insertRecord`, `updateRecord`, `softDeleteRecord`, `restoreRecord` and `recordAudit` (`write.ts`). `lockProjectChanges` and `lockOrganisationChanges` (also `write.ts`) take a project's change counter and an organisation's own, for a service that must lock a record before it writes: queue on the counter first, as the helper does, then take the record lock, or it can deadlock with a helper write. Use the first for a record of a project and the second for a record of the organisation alone (a membership, a role); they are two functions, not one with a null, so a call cannot change meaning by accident. They share one internal lock and number nothing. The one exception is a new project or a new organisation: its counter references the row, so `insertRecord` takes it after the row, and gives it seq 1 in its own sequence. Nothing else can write to a record that is not committed yet, so no writer can be waiting on that counter.
- `tenantTable`, `securityTable`, `securityChildTable` and `standardColumns` (`columns.ts`); one file per table in `schema/`.
- `tableWriters()` and `declareServiceWrittenTable` (`columns.ts`): the registry of who writes each security table and each service-written table, and the declaration of the second kind (see the rules below).

**Rules you must not break**

- Tenant records are written only through `write.ts`, with the transaction handle. It numbers the change, logs one `change_event` and keeps sensitive values out of it. An update that changes no field checks the version, then writes nothing.
- Define tenant tables with `tenantTable()` and login tables with `securityTable()`, and list each security table in `SECURITY_TABLES`. Plain `pgTable` is for the other install-level, log and counter tables.
- Security tables (sessions, credentials, one-time codes, invites, admin reset links, personal API tokens) are written directly, never through `write.ts`, and audited instead of change-logged. Each has one writer, a folder of `packages/core/src/`: `src/auth/`, unless the table declares another with `securityTable(..., { writtenBy: { service, reason } })`, which must say why in one line. A service-written table declares its writer the same way (`declareServiceWrittenTable`). `tableWriters()` is the one record of all of them, and `write-helper-scan.test.ts` reads only that: it fails when a tenant table is written outside `write.ts`, when a security table, a service-written table or the child table of a security table is written from any folder but its declared writer, when a writer that is not the default has no one-line reason, and when a declared folder does not exist.
- A security table has no `organisation_id`, with one declared exception: `securityTable(..., { organisationScoped: { organisationId, reason } })` adds the column's foreign key (`<table>_organisation_fk`) and records the table and its reason (`organisationScopedSecurityTables()`). `invite`, `access_reset`, `api_token` and `access_grant` use it (`access_grant` has composite keys to `project`, `person` and `role` on `organisation_id`, so a grant can only tie a person to a project and a role of their own organisation, and it is the one security table the sensitive service writes, not the auth service), and `invite_role`, the child table of `invite` (`securityChildTable`, listed in `SECURITY_CHILD_TABLES`), carries `organisation_id` too: both of its foreign keys are composite on it, so an invite can never attach another organisation's role. `access_reset` has a composite key to `org_membership` on (`organisation_id`, `user_id`), so a reset link can only be for a member of the organisation that issued it, and `api_token` has the same key plus one to `project` on (`organisation_id`, `project_id`), so a personal API token can only be its owner's, in an organisation they belong to and a project of it. The CHECK that no key is listed twice in a token's sensitive scope calls `osfpm_text_array_is_distinct`, a function the migration writes by hand (a CHECK cannot hold a subquery). `invite_role` has no retention class of its own: its rows are deleted with their invite (`ON DELETE CASCADE`), so the invite's `transient` cleanup covers both. `schema.test.ts` reads these records from code, so a table cannot gain the column without declaring it. The write helper refuses every security table and child table (`SecurityTableWriteError`, tested in `write-security-tables.test.ts`), though these two have an `organisation_id` it would otherwise accept.
- `user`, `installation`, `user_access_profile` and `user_preferences` are the service-written tables listed in `SERVICE_WRITTEN_TABLES` (`schema/service-written-tables.ts`): install-level tables with no `organisation_id`, written only by their declared writer, never through `write.ts`, and audited instead of change-logged. The same scan enforces it. Adding a table, or changing a writer, is a change to that list in the same commit. First-run setup is in `src/auth/`, the writer of the first two. The sensitive service writes the access profile, and the preferences service writes `user_preferences`, a person's delivery preferences. A person with no account keeps theirs in the nullable column `person.communication_preferences` instead, which the write helper writes like any other column.
- A tenant table with no `project_id` calls `registerProjectResolver` or `declareOrganisationLevel` next to its definition. A schema test requires one of the two.
- Tag sensitive columns with `markSensitive`. Never put a sensitive value in a log, an error or an audit detail.
- IDs come from `newId()` (UUIDv7). The database never makes them.
- Migrations are forward-only. Put a comment above each hand-written SQL block, such as the append-only triggers, and say so in the commit message.
- Migrations may change metadata of existing rows (retention class, defaults) without audit events; they never change security state (revoke, disable, grant).
- Name foreign keys `<table>_<target>_fk`. A key that starts with `organisation_id` keeps the reference inside one organisation.

**Tests:** `columns.test.ts` covers the registers `columns.ts` keeps (retention classes, security tables with their declared exceptions, writers) with throwaway tables. `write-helper-scan.test.ts` covers who may write which table, from the registry. `whole-row-scan.test.ts` parses every source file of `packages/core/src` and fails on a Drizzle read that selects every column of `person` or `user` (`select()` from or joined to one, the table as a value of the list, `getTableColumns`, the relational API, raw `select *`): it skips only the files that end in `.test.ts` and allows nothing else, so a read lists its columns (CLAUDE.md, Data rules). `schema.test.ts` checks every table's structure and constraints. `change-log.test.ts`, `write-project.test.ts` and `write-organisation.test.ts` cover the write helper: the last two cover a new project and a new organisation, the tables whose counter comes after the row, and `write-organisation.test.ts` also pins that order and, on PostgreSQL only, creates organisations at the same time. `write-security-tables.test.ts` pins that the helper refuses every security table, `invite`, `invite_role`, `access_reset` and `api_token` included. `lock-changes.test.ts` covers `lockOrganisationChanges` (it numbers nothing; on PostgreSQL only, that it queues behind and in front of an organisation-level write, and that it never waits on a project's counter or another organisation's). `production-structure.test.ts`, `library.test.ts` and `retention-class.test.ts` cover their tables. `migrate-lock.test.ts` checks, with the migrator replaced, the order of what `migrate` does around it and that it runs on the one connection that holds the lock. `migrate.test.ts`, on PostgreSQL only, runs the real migrator: two migrators at once, one that waits for a held lock, a pool of one connection, and a failed migration. `test-support.ts` provides the PGlite and PostgreSQL targets, `interleave` (two transactions held against each other, with an optional look at the locks while the second is blocked) and `guardTeardown`, the handler for a pool a test owns that lets the shutdown error of a forced drop (57P01) pass at teardown and nothing else; `test-support.test.ts` tests it, and the target's pool and the pool of `migrate.test.ts` use it.
