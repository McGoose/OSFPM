# sensitive

Crew personal data: dietary, medical, accessibility, emergency, identity, financial, representation and compliance. This folder is the one door to it. `service.ts` is the only code that reads or writes the `person_sensitive` table, and the other files here are the only code that reads or writes `user_access_profile` and `access_grant`, the two tables of the access needs model.

**Entry points**

- `readSensitive`, `writeSensitive` and `deleteSensitive` (`service.ts`) work on one category of one person.
- Access needs (decision D-69, below): `createAccessProfile`, `readAccessProfile`, `updateAccessProfile` and `deleteAccessProfile` (`access-profile.ts`); `createAccessGrant`, `revokeAccessGrant` and `shareWithSuggestedRoles` (`access-grants.ts`); `listGrantedAdjustments` (`adjustments.ts`); `endAccountAccessSharing` (`account-sharing.ts`), the call the account-deletion service must make.
- `complianceReport` returns counts per department, with no names, ids or payloads.
- `payloadSchemas`, `SENSITIVE_CATEGORIES`, `ACCESS_FIELDS`, `ACCESS_GROUPS` and `MEDICAL_FIELDS` (`schemas.ts`); `SENSITIVE_PERMISSIONS` (`permissions.ts`); `ACCESS_SUGGESTED_ROLES_SETTING` and `readSuggestedRoles` (`suggested-roles.ts`).
- `SensitiveChangeNotifier` queues a notice when staff change a person's data. The default queues nothing.

**Access needs: three layers** (decision D-69)

Most disabled and neurodivergent crew never disclose, so access needs are recorded as practical adjustments, owned by the person and shared only with people who need them. Nothing asks for a condition or a diagnosis. This follows the TV Access Project's Access Passport and Channel 4's Access Rider; `ACCESSIBILITY.md` at the root says it in words for the public.

1. **The person's profile** (`user_access_profile`). One per account, in the structured shape of the `accessibility` payload: a schedule (earliest and latest times, longest day, breaks, notice), physical needs, transport, communication, environment, support, and free-text notes. Only the person creates, reads, changes or deletes it: not an organisation owner, not an administrator, not a personal API token. It has no organisation and no project, so it stays when a production wraps and goes only when the person deletes it or their account goes. Retention class `account-lifetime`: kept while the account exists, with no period and no project date, so a project's wrap or a purge never reaches it. The grants it opens stay `crew-health`, the class of the data a production sees.
2. **The production's record** (`person_sensitive`). For a person without an account, staff who hold `sensitive:edit:accessibility` enter the same structured adjustments, and the retention class deletes it after wrap. For a person with an account, writing their `accessibility` row is refused (`UseAccessProfileError`, 422 `use-access-profile`): their adjustments live in their profile. Medical data stays here for everyone, as the organisation's record.
3. **Grants** (`access_grant`). A production sees nothing of a person's adjustments or medical data until the person grants it, field by field, to a role, on one project. Default deny.

**Grants**

- **Who makes one.** The person themselves, when they have an account. For a person without one, a user who holds `sensitive:edit:<category>` on the project, who records how and when the person agreed (`method`, `at`, and an optional `note` of up to 200 characters with no health details). Staff cannot grant for a person with an account.
- **Who revokes one.** The person, or staff who edit, for a grant that was recorded on someone's behalf. A role has one live grant: making another for it replaces it, in one step. A revoke opens nothing from the moment it commits. Deleting their profile revokes all of the person's accessibility grants, in every project and organisation, in the same transaction, so a profile made later opens nothing until they grant again; their medical grants stay, because those open the organisation's record, not the profile. A share with the usual roles holds the person's user row `FOR KEY SHARE` and then the profile row `FOR SHARE` while it works, so a deletion of the profile waits for it, and the other way round.
- **When the account goes.** Accounts are only soft-deleted, and there is no account-deletion service yet. A grant is not live while its person's account is deleted (see "When it is live"), so a deleted account's grants open nothing, but nothing revokes them: they and the profile would open again if the account were restored. `endAccountAccessSharing(tx, userId, reason)` is the door's function that service must call, under the user row taken `FOR UPDATE` (a TODO in its JSDoc says so). It revokes every live accessibility **and medical** grant of every person the account is, in every project and organisation, erases the access profile and the account's delivery preferences (`eraseUserPreferences`), and writes one `access.account-sharing-ended` event with counts and the reason (`account-deleted`), and none for each grant. It works on an account already marked deleted. Restoring the account reopens nothing: the person has to make a profile and grant again. The organisation's own medical record stays, because it is the organisation's; the grants that opened it end. The order is the user row, then the profile row, then the grants (CLAUDE.md, Data rules). Every writer of grants and of the profile follows it: `createAccessGrant`, `revokeAccessGrant`, `shareWithSuggestedRoles`, `createAccessProfile`, `updateAccessProfile` and `deleteAccessProfile` take the person's user row `FOR KEY SHARE` first (`holdAccount`), so a deletion of the account and any of them queue on the user row and cannot deadlock. The ones that make something derived from the account refuse a deleted account with `AccountDeletedError` (422 `account-deleted`, audited as `access.refused` with that reason; only the account's own holder reaches it, since nobody else grants or makes a profile for them): a grant, a share with the usual roles in either category and a preview of one, and a profile. So no live grant and no profile of a deleted account is left behind. The ones that only end or change what exists (a revoke, changing or deleting the profile) do not look at the answer: a deleted account may always end what it shared.
- **What it names.** A role, which must be a live role of the organisation that is an organisation template or belongs to this project (one answer, `RoleNotAvailableError`, 422 `role-not-available`, for a missing, deleted or foreign one), and fields: keys of the category's payload, each once (`ACCESS_FIELDS`, or `conditions`, `medication` and `notes` for `medical`).
- **When it is live.** It is not revoked, the project is not deleted, delivered or archived and is not past its `wrap_date` (by the date in the project's own time zone, and live through the wrap date itself), the person still has a proposed or confirmed `project_person` row on the project, and the person's account, if they have one, is not deleted. The last one matters for the medical grants, which open the organisation's own record: that record outlives the account, so without it a deleted account's grant would go on opening it. This is worked out when it is read (`grant-reads.ts`, `liveness.ts`), never stored, so no job is needed: a project that wraps, a person who is released, an account that is deleted and a grant revoked a moment ago stop opening anything at once, and the grant row never changes.
- **Share with the usual roles.** `shareWithSuggestedRoles` makes one grant for each role the organisation usually shares each group with (the setting `access.suggested-roles`, a map from a group, and `medical`, to role ids; empty by default and read only until the settings service of P-04 writes it), covering the fields the person has filled in those groups. `notes` is never included, in either category: free text goes only by an explicit grant. With `preview: true` it writes nothing and says who would see what, which is what a confirmed call then makes. When no role is suggested for the groups asked about (the setting is missing, or holds nothing usable for them), the answer is an empty preview with `reason: 'no-suggested-roles'`, whether or not the call asked for a preview: nothing is read or written, no `access.shortcut-used` event either, so a client can say the usual roles have not been chosen instead of showing a share that reached nobody. A call that finds roles but nothing the person filled in is still an ordinary result with no grants.
- **The constraint view.** `listGrantedAdjustments` gives, for each person on a project, only the adjustments they granted to a role the reader holds there and have filled in. It is what a schedule or call sheet check can plan around: no reasons, no medical data, no field that was not granted.

**Who reads what**

| Reader                                                          | `accessibility`                                                                                                              | `medical`        |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| The person themselves                                           | All of it: their profile, or the production record if they have no account                                                   | All of it        |
| Holds `sensitive:read:<category>` on the project                | Only the fields that live grants to a role they hold in an active membership of that project cover; with none it is a denial | The same         |
| Holds `sensitive:edit:<category>`, for a person with no account | The whole production record, which they need to edit it                                                                      | The whole record |
| A personal API token                                            | What its owner reads through the token's sensitive scope; grants still apply; never the person's own way in                  | The same         |
| Anyone else, an owner or an administrator included              | Denied                                                                                                                       | Denied           |

`dietary` and `emergency` keep the rules of P-02e: the read permission on a project where the person is engaged is enough, and no grant is needed.

**Rules you must not break**

- Nothing else may name `person_sensitive`, `user_access_profile` or `access_grant` (the last two are the tables the registry `tableWriters` says this service writes). `source-scan.test.ts` fails if other code does.
- For the categories other than the two of the access needs model, access is the person themselves, or a holder of `sensitive:read:<category>` or `sensitive:edit:<category>` on a project where the person is `confirmed` or `released`. Owners and admins get nothing automatically.
- `accessibility` and `medical` are read only through live, person-approved grants: the sensitive-read permission alone is never enough (see the table).
- A personal API token (`SensitiveContext.credential`) reaches the same data only through its explicit sensitive scope: it must list the permission's key, the organisation's sensitive switch must be on, and the token's owner must hold the permission on a shared project at that moment (`hasProjectPermission` narrows by the credential). A token never takes the person's own way in, so it cannot read, change or grant for its owner's own data. Its writes are the token's in the change log (actor `token`, made for its owner), and every read and every denial through a token is audited with the token's id (actor `token`, details `tokenId` and `userId`).
- Audit every allowed read and every denial, with the category and never a value. A read of `accessibility` or `medical` also carries the number of fields it returned, and never their names: a field name alone can hint at a condition. A denial or a refusal throws after its audit event is written, so catch it inside the transaction and commit.
- A grant, a revoke and the shortcut are audited as `access.grant-created`, `access.grant-revoked` and `access.shortcut-used`, a profile change as `access.profile-created`, `-updated` and `-deleted` (the last holds the number of grants it revoked, and no event is written for each of them), the end of an account's sharing as `access.account-sharing-ended` (counts and a reason code, and no event for each grant), and a refusal of a rule as `access.refused` with a reason code from a closed list. They hold ids, counts and codes only. Profiles and grants are service-written: audited, not change-logged.
- Never log, email or put a payload value, a field name of the access needs or a consent note in an error, an audit detail, a change event or a notifier call.
- A notifier only enqueues, through the transaction it is handed, and never sends. The write and its notice share one savepoint, so they succeed or fail together. A staff save that changes nothing writes nothing and queues no notice.
- An unknown or deleted person, project or grant is denied like any other, so ids cannot be probed. A revoke of a grant the caller may not end is the same not found as for one that is not there.
- A profile is deleted in one place, `deleteProfileRow`, which only the person's `deleteAccessProfile` and the account's `endAccountAccessSharing` call: nothing deletes one because time has passed (`profile-erasure-paths.test.ts`; retention class `account-lifetime`).
- A new category needs a payload schema, a retention class in `service.ts` and a migration for the table's CHECK.
